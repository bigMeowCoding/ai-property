## 证据分层

先建立证据台账，避免把推断写成事实：

| 层级 | 含义 | 写法 |
|---|---|---|
| 已知事实 | 用户提供、真实数据、一手观察或已核对来源 | 陈述事实并标来源/时间 |
| 知识依据 | 知识库中的概念、案例或原始资料 | 链接到具体页面或来源 |
| 推断 | 从事实和框架推导出的判断 | 写出推导过程与置信度 |
| 假设 | 尚未获得证据但决策需要成立的前提 | 标“待验证”并绑定实验 |

优先级一般为：真实行为与交易证据 > 可观察的任务完成情况 > 访谈陈述 > 问卷态度 > 团队直觉。不同证据回答不同问题，不能机械混成单一分数。

## 决策定义

在分析前补全：

- 决策：现在要决定什么？不决定会怎样？
- 期限：何时必须作出决定？可否分阶段？
- 目标：希望改变哪类用户的什么行为？企业目标是什么？
- 约束：时间、成本、技术、合规、品牌、组织和渠道。
- 决策权：谁负责决定，谁负责提供专业判断？
- 可逆性：决定是否容易撤回？不可逆决策需要更强证据。

## 产品机会评估

只讨论问题与机会，不预设具体方案：

1. 要解决什么问题？不解决的代价是什么？
2. 为谁解决？具体发生在什么情境？
3. 当前如何解决？旧体验与替代品是什么？
4. 问题频率、强度和覆盖规模如何？证据是什么？
5. 成功后希望用户行为和业务结果如何变化？
6. 竞争格局与替换成本如何？
7. 为什么此团队适合解决？优势或独特资源是什么？
8. 时机、渠道和必要条件是否具备？
9. 最大的不确定性与失败方式是什么？
10. 结论是继续、暂缓、放弃，还是先补证据？

市场规模没有可靠数据时，给出估算公式与变量，不编造 TAM。新产品和现有产品改进使用同一套机会标准。

## 用户模型

把用户写成“需求 × 情境 × 当前行为”，不要只写年龄、性别和职业。

至少检查：

- 异质性：哪些用户差异会改变产品选择？
- 情境性：何时、何地、由什么触发需求？
- 可塑性：产品、规则或反馈会怎样改变行为？
- 自利性：用户实际追求什么效用？谁承担成本？
- 有限理性：信息、认知、时间与情绪如何限制决策？

用户模型的可检验形式：

> 当 `[用户/需求]` 在 `[情境]` 遇到 `[刺激或约束]` 时，会因为 `[偏好/认知]` 采取 `[行为]`，产生 `[结果]`。若改变 `[产品变量]`，预计行为将 `[变化]`。

Persona 必须来自真实数据，用于统一团队理解；它不能替代行为模型，也要定期更新。

## 用户价值与交易模型

### 用户价值

使用：

```text
用户价值 = 新体验 - 旧体验 - 替换成本
```

逐项分析：

- 新体验：解决了什么任务，增加了哪种效用？属于底线、够用、越多越好还是惊喜？
- 旧体验：用户现在的做法、竞品、不行动分别提供什么效用？
- 替换成本：金钱、学习、时间、数据迁移、信任、关系、流程和心理成本。
- 分群差异：同一方案对不同情境用户的净价值是否相反？

除非有数据支持，不把三项强行量化为精确数字。

### 交易可持续性

检查：

- 效用：各方分别获得什么？
- 成本：用户与企业各自的直接成本、交易成本和机会成本。
- 边际：再增加一个用户、功能或交易，额外效用、成本与利润如何变化？
- 供需：价格、稀缺性、容量和匹配机制如何影响交易？
- 分配：价值由谁创造、谁获得、谁承担损失？是否公平且可持续？

好产品既要通过价值/可用性/可行性前置验证，也要在市场中有效用、有收益、可持续。

## 需求拆解与优先级

### 从目标到需求

按以下顺序拆解：

```text
目标 → 用户情境/任务 → 问题 → 期望结果 → 能力 → 功能/规则 → 验收与指标
```

保持 MECE 但不为形式强拆。每项功能必须能回溯到用户问题或必要约束。

### 需求类型

| 类型 | 判断 | 策略 |
|---|---|---|
| 底线/必备 | 缺失即无法完成核心任务或用户直接离开 | 优先满足 |
| 期望 | 做得越好，效用通常越高 | 按边际收益投资 |
| 惊喜 | 超出预期但非核心任务所需 | 有余量再做 |
| 反向 | 增加后会降低部分用户价值 | 避免或分群提供 |
| 约束 | 合规、安全、可靠性等进入市场的必要条件 | 作为门槛，不与普通功能混排 |

### 排序

先过门槛，再评分：

1. 是否服务当前目标和关键用户任务？
2. 是否是合规、安全、依赖或可行性门槛？
3. 证据强度与影响范围如何？
4. 成本、时效、依赖、可逆性和机会成本如何？

可选 ICE：`Impact × Confidence × Ease`。明确每项分数的证据；数据不足时使用高/中/低，并说明未知。不同性质的事项不要伪装成可精确比较的同一分数。

## 产品探索与验证

### 区分四种产物

| 产物 | 目的 | 是否必须完整 |
|---|---|---|
| 访谈/概念测试 | 理解问题与价值主张 | 否 |
| 原型 | 验证流程、可用性和体验预期 | 不必可生产运行 |
| MVP | 用最小成本验证核心概念或市场行为 | 不一定是完整产品 |
| 基本产品 | 交付不可再删的最小完整价值 | 是 |

### 假设台账

| 假设 | 类型 | 当前证据 | 风险 | 验证方法 | 通过标准 | 失败动作 |
|---|---|---|---|---|---|---|
|  | 价值/可用性/可行性/商业 |  | 高/中/低 |  |  |  |

优先验证“重要且最不确定”的假设，不先做容易但不关键的实验。

### 验证方法

- 问题证据：情境访谈、现场观察、日志/客服记录、行为数据。
- 价值验证：概念测试、意向行为、预订/付费、礼宾式服务、MVP。
- 可用性验证：关键任务原型测试；保持安静，不提示用户。
- 可行性验证：技术 spike/POC、成本评估、合规与运营评审。
- 商业验证：单位经济、边际成本、渠道与留存小规模实验。

把“连续六位目标用户理解价值并完成关键任务”作为高保真原型测试的经验门槛之一，同时结合任务成功率、问题严重度和用户分层，不把它当统计显著性结论。

## 指标、实验与发布

### 指标

为每个决策指定：

- 一个主指标：直接对应目标行为或价值结果。
- 2–4 个护栏指标：防止增长以伤害体验、收入、公平、安全或稳定性为代价。
- 领先指标与滞后指标：区分早期信号和最终结果。
- 观察窗口：避免过早下结论。

NPS 可衡量推荐意愿，但不能单独证明留存、收入或具体问题已解决。

### A/B 测试

只在变量可控、样本可分、干扰可控且风险可接受时使用。预先写明假设、主指标、护栏、样本/周期、停止规则和分群分析。不要用 A/B 测试替代探索性用户研究。

### 渐进发布

按顺序设计：内部/特约用户 → 小比例 beta → 分群或区域灰度 → 扩大范围 → 全量。始终准备功能开关、回滚条件、监控和新旧版本对比。

## 团队职责边界

| 角色 | 核心责任 |
|---|---|
| 产品经理 | 评估机会、定义并验证正确的产品 |
| 产品设计 | 设计并验证完整用户体验 |
| 开发/技术 | 判断实现方式、技术可行性与工程质量 |
| 项目管理 | 计划、依赖、进度、预算与交付协调 |
| 产品营销 | 定位、发布、渠道、市场沟通与销售支持 |

角色边界不等于接力。让设计和开发在探索早期参与，让产品经理亲自接触用户并对产品判断负责。

## 常见陷阱

- 方案先行：先画功能，再寻找问题。
- 用户同质化：用一个宽泛画像代表全部情境。
- 忽视旧体验：只与“什么都不做”比较，不与真实替代方案比较。
- 忽视替换成本：新体验更好，却不足以促成迁移。
- 指标替代理解：只看数据相关性，不理解用户为何行动。
- MVP 膨胀：每个团队都把自己的“最小需求”塞入版本。
- 评分伪精确：没有证据仍给出 TAM、ROI、ICE 的精确数字。
- 角色混淆：让产品经理替代项目、营销、设计或技术职责。
- 发布即结束：没有灰度、回滚、反馈和后续决策门槛。
