# Spring 事务模式

先写清原子性不变量和外部副作用，再选择事务注解、锁与数据库约束。

## 工作流

1. 列出操作前状态、所有写入、外部调用、成功状态和每个失败点。
2. 标出必须共同提交的数据库写入，以及不能放进长事务的网络或流式调用。
3. 选择最小事务边界，再用唯一约束、版本字段或条件更新处理并发。
4. 通过故障注入和并发测试证明无部分提交、重复记录或非法状态组合。

## 规则

- `@Transactional` 放在可被 Spring 代理调用的 Application/Service 公共方法上。
- 同类自调用、私有方法和手工 `new` 出来的对象不会获得预期代理语义。
- 默认回滚规则只覆盖未检查异常；转换异常时明确是否需要 `rollbackFor`。
- `readOnly = true` 只在确认调用链不写入时使用，不能当成安全边界。
- 不在数据库事务中等待长时间模型响应；把持久化阶段与外部流式阶段显式拆分。
- 应用层预检查用于友好错误，数据库唯一约束或条件更新用于并发最终防线。
- 优先乐观锁和状态条件更新；只有证据表明需要时才使用悲观锁或更高隔离级别。
- 提交后副作用使用明确的 after-commit 机制；监听器自身写库时定义新事务和失败策略。

## DevLoop 事务清单

- 创建项目与首条消息共同提交。
- 级联删除项目与子资源保持原子。
- 覆盖 Spec 时同步处理当前标记和 Tasks 确认失效。
- 保存、结构校验与确认必须防止基于过期内容提交。
- 用户消息先可靠持久化；模型失败不得删除它，重试不得重复生成记录。
- 同一项目重复耗时操作必须具备互斥、幂等键、版本检查或条件更新之一。

## 验证

- 在每个写入点和外部调用点注入失败，断言最终数据库状态。
- 用真实 MySQL 并发执行相同项目操作，断言唯一性和合法状态机。
- 证明客户端断开、上游超时和异常转换不会扩大事务或吞掉失败。

## 常见失误

- 在 Controller 或 private 方法上添加事务注解。
- 在事务内完整等待 SSE 或模型网络响应。
- 用 `exists` 后 `insert` 代替唯一约束，产生检查后使用竞态。
- 捕获异常后不再抛出，导致事务意外提交。
- 无依据使用 `REQUIRES_NEW`，制造调用方看不见的部分提交。
