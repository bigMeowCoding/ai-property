# REST API 规范

从调用方可观察契约出发，保持成功、失败和特殊媒体类型的语义稳定。

## 工作流

1. 搜索现有 Controller、DTO、异常处理、OpenAPI、前端调用和契约测试。
2. 写清方法、路径、输入、成功响应、失败分类、幂等性和资源归属。
3. 在请求边界做结构校验，在 Application/Service 做业务与归属校验。
4. 用 Controller 切片或 API 集成测试验证 JSON、状态码、响应头和负向路径。

## 约束

- Controller 只做协议适配；每个端点调用一个清晰的应用用例。
- 请求和响应使用独立 DTO；输入 DTO 使用 `jakarta.validation`，JPA Entity 不直接出现在 API。
- 普通 REST 使用项目唯一的成功与错误格式，不为新端点再造一套 envelope。
- 常用映射：结构/参数错误 `400`、资源不存在 `404`、状态或唯一性冲突 `409`、模型上游失败 `502`、上游超时 `504`、未分类内部错误 `500`。
- 错误响应提供稳定业务码和安全消息；不返回堆栈、SQL、密钥、Authorization 或供应商原始响应。
- DELETE 的响应体和状态码、PUT/PATCH 语义、分页基数都服从现有契约。
- Spec 未冻结的路径、字段、ID、时间格式或状态码只能列为待确认项或明确标注的方案，不能写成现有契约。
- 对列表限制 page size，并校验排序字段白名单；不要直接序列化 `PageImpl` 作为长期契约。

## 特殊响应

- SSE/流式接口使用独立媒体类型和事件协议；流开始后不能再假设可返回普通 JSON 错误。
- 文件下载明确 `Content-Type`、安全规范化后的 `Content-Disposition` 和失败条件。
- 流式和下载错误仍必须有调用方可区分的语义，并与普通业务错误码对齐。

## 验证清单

- 合法输入、缺字段、超长、非法枚举、错误资源归属。
- 不存在、冲突、上游失败、未知异常的状态码和业务码。
- 响应不泄露 Entity 字段、内部异常或敏感请求头。
- 前端消费者或契约测试能够解析所有成功与失败分支。

## 常见失误

- 每个 Controller 定义不同的响应包装。
- 捕获 `Exception` 后统一返回 `200` 或把供应商异常原样返回。
- 只依赖前端校验，服务端接受越界文本或跨项目 ID。
- 在 Controller 中处理事务、重试或状态机。
- 把普通 JSON 错误写入已经开始的 SSE 数据流。
