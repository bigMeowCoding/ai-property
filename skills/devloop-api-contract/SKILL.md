# DevLoop API 契约

把 Spec、服务端实现、Web 消费者和契约测试对齐为一个可追踪的接口基线。

## 必读参考

修改接口前读取 [contract.md](references/contract.md)，然后读取两端当前 Spec、已有 DTO、调用代码和测试。参考文件只记录已确认不变量；未冻结字段必须从当前事实源确认，不能自行补造。

## 工作流

1. 识别变更属于项目、消息、模型流、文档、状态、设置还是导出。
2. 列出生产者与所有消费者，写清字段、可空性、枚举、顺序、错误和兼容策略。
3. 先更新共享契约或契约测试，再分别修改服务端和前端。
4. 搜索旧字段与旧枚举，验证正常、失败、取消和过期状态。

## 契约规则

- 普通 REST 使用统一成功和错误表达；SSE 与下载按媒体类型使用专用响应。
- 错误至少可区分参数错误、资源不存在、状态冲突、模型上游失败和内部错误。
- 状态枚举只有一个事实源；未知值必须显式失败或采用已约定兼容策略。
- 所有子资源通过项目归属校验，前端传入 projectId 不能替代服务端验证。
- SSE 事件区分开始、增量、完成、错误和取消，并且每个流只有一个终态。
- 下载内容来自数据库最后保存版本；ZIP 仅在当前 Spec 与 Tasks 均确认时可用。
- 字段删除、改名、改变可空性或枚举语义属于破坏性变化，必须同步消费者和测试。

## 验证

- 服务端契约测试断言 DTO、状态码、业务码、事件序列和响应头。
- Web 端使用真实契约 fixture 验证解析、状态渲染、错误与取消。
- 主链路覆盖创建项目、对话、生成/确认 Spec、生成/确认 Tasks 和导出。
- 最终搜索两端旧字段、旧事件和旧状态，记录未迁移消费者。

## 常见失误

- 后端修改字段但只修 TypeScript 类型，不检查运行时解析。
- REST、SSE 和下载各自发明不兼容的错误语义。
- 把供应商流事件作为 DevLoop 公共事件。
- 前端根据按钮状态推断后端允许确认或导出。
- 在契约尚未确认时用示例字段填补空白并当作事实。
