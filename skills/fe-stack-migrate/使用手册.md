欢迎使用前端统一发布平台，在接入之前请您仔细阅读本文档，文档可以解决大部分接入问题。

**控制台入口**：从 **研发运维平台**（`https://idp.busyming.com`）打开「前端发布平台」。统一门户 `portal.busyming.com` 已停用，不要再从那里进。用户侧访问域名是 `https://fe-stack.busyming.com`。

**一套控制台管理全部环境（dev / test / uat / pre / prod）**；版本、灰度、配置、流水线、日志按环境隔离；项目、成员、静态页、图床跨环境共享。环境靠路径区分。版本管理页用环境条切换当前操作环境。

**对外正式入口必须用生产地址**（路径不带 `{env}`）；非生产地址仅联调 / 预览。

控制台操作说明（入口、自动发版、流水线选型、图片处理、域名校验等）以语雀《前端发布平台使用手册》为准；本文补充代码改造与 Skill 细节。

#### 流水线改造
使用统一发布平台托管项目需要找运维改云效流水线。**两套模板**，建议先改 **dev**，验证后再改其它环境。各环境回调同一运行时域名，靠 body 里的 `ENV` 区分环境。

| 模板 | 适用 | 业务仓 |
| --- | --- | --- |
| **新架构-前端统一发布模板** | 平台域名直连，或自定义域名走**网关直连**（新业务、域名无过多存量） | Dockerfile / nginx **不用改** |
| **新架构-前端统一发布模板-nginx** | 已投产，要**完全保留以前的访问路径** | **必须改** `Dockerfile` + `nginx-default.conf` |

自定义域名两种落地：

| 方案 | 流量 | 何时选 |
| --- | --- | --- |
| **网关直连** | 请求到网关 → 网关把路由打到 instance | 新业务；该域名没有过多存量业务 |
| **nginx + Docker** | 业务镜像内 nginx 反代到平台 | 已投产，完全沿用旧访问方式 |

```bash

 npm install -g pnpm@10 && pnpm install --no-frozen-lockfile && pnpm run build:${env} && tar zcvf ${DATETIME}.tar.gz dist/ && curl https://gosspublic.alicdn.com/ossutil/install.sh | sudo bash && whereis ossutils && ossutil cp ${DATETIME}.tar.gz oss://portal-fe-${env}/${CI_SOURCE_NAME}/build/ -e https://oss-cn-hangzhou-internal.aliyuncs.com -i ${PORTAL_FE_OSS_AK} -k ${PORTAL_FE_OSS_SK} -r --update && JSON_BODY=$(cat <<EOF
 {
 "CI_SOURCE_NAME": "${CI_SOURCE_NAME}",
 "DATETIME": "${DATETIME}",
 "ENV": "${env}",
 "BUILD_EXECUTOR": "${BUILD_EXECUTOR}",
 "BUILD_NUMBER": "${BUILD_NUMBER}",
 "PIPELINE_ID": "${PIPELINE_ID}",
 "CI_COMMIT_TITLE": "${CI_COMMIT_TITLE}",
 "CI_COMMIT_REF_NAME": "${CI_COMMIT_REF_NAME}"

 ) && curl -X POST "https://fe-stack.busyming.com/instance/webhook/build" -H "Content-Type: application/json" -d "$JSON_BODY"
```

说明：

+ `CI_SOURCE_NAME` 必须等于平台项目编码（**云效应用名**）
+ 构建包上传路径必须是 `{projectCode}/build/{DATETIME}.tar.gz`，与 webhook 里的 `DATETIME` 一致（OSS 桶 / 前缀以运维模板为准）
+ 回调地址统一为：`https://fe-stack.busyming.com/instance/webhook/build`（**不再**按环境分 `{env}-fe-stack` 主机）；环境由 body 字段 `ENV`（如 `dev` / `test` / `prod`）决定
+ 生产环境可额外传 `TAG` / `tag`，用于版本 tag；未传时会用 `v{BUILD_NUMBER}`
+ **nginx 模板**额外构建业务镜像，并注入 `ENV`（供 Dockerfile 替换 conf 中的 `{env}`）

##### 选用「…-nginx」模板时：改 Dockerfile + nginx

**Dockerfile**（ADD conf 之后）：

```dockerfile
ARG ENV
ADD ./nginx-default.conf /etc/nginx/conf.d/default.conf
RUN if [ "$ENV" = "prod" ]; then \
      sed -i 's|{env}/||g' /etc/nginx/conf.d/default.conf; \
    else \
      sed -i "s|{env}|${ENV}|g" /etc/nginx/conf.d/default.conf; \
    fi
```

**nginx**（`{projectCode}` 换成真实编码；`{env}` 留给 Dockerfile）：

```nginx
location / {
  proxy_pass https://fe-stack.busyming.com/instance/p/{env}/{projectCode}/;
  proxy_ssl_server_name on;
  proxy_set_header Host fe-stack.busyming.com;
  proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
  proxy_set_header X-Forwarded-Proto $scheme;
}
```

旧入口若是子路径，对该 path 做同样反代。`proxy_ssl_*` / Cache / CORS header 可按需保留。生产构建后路径无 `{env}/`。

构建成功后平台会发机器人通知（系统默认通知 + 项目若单独配置了构建通知也会再发一份），失败不影响版本记录落库，可在操作日志里看到结果。

##### 配置路由基础入口路径
`appBaseName` =「用户浏览器里应用挂在哪个路径前缀下」。

接入前先确认**项目场景**（决定推荐访问方式）：

| 场景 | 典型情况 | 推荐访问 | basename |
| --- | --- | --- | --- |
| **A. 平台域名直连** | 中台页、从研发运维平台菜单进 | 直连 `fe-stack.busyming.com` | 平台注入的 `window.__APP_BASE__` |
| **B1. 自定义域 · 网关直连** | 新业务、域名无过多存量 | 自有域；**网关**路由到 instance | 已有 `VITE_APP_BASE_NAME` |
| **B2. 自定义域 · nginx** | 已投产，完全保留旧访问方式 | 旧域 / 旧 path；容器 nginx 反代 | 同上 |
| **C. H5 嵌企微 / 微信 / 小程序** | 在容器 webview 里打开 | 在 A 或 B 之上选访问域 | 同上；**另需**改可信域（见 §1） |

A 与 B 不要混用访问约定：业务域反代后若仍按 instance 注入当 base，或误把 base 设成 `/`，都会 404。代码可用 `resolveAppBaseName` 兼容两种；**对外入口按主场景选一种**。

纯 A / 纯 B **不必**一上来改企微/微信可信域；只有场景含 C 才处理。

###### 平台提供的域名直接访问（场景 A）
+ 打开的就是**平台提供的**地址，例如：
  - 生产：`https://fe-stack.busyming.com/instance/p/{projectCode}/pages/...`
  - 非生产：`https://fe-stack.busyming.com/instance/p/{env}/{projectCode}/pages/...`（如 `{env}=dev`）
+ 平台会注入 `window.__APP_BASE__`（与当前访问路径一致）：
  - 生产：`/instance/p/{projectCode}/`
  - 非生产：`/instance/p/{env}/{projectCode}/`
+ 此时 `pathname` 以该前缀开头 → **用注入值**
+ **`VITE_APP_BASE_NAME` 禁止改动**；接入只需补 `resolveAppBaseName` 运行时分支
+ 菜单入口改成**生产**平台 URL；非生产 URL 仅联调
+ 流水线模板：`新架构-前端统一发布模板`；Dockerfile/nginx 不动

###### 自定义域名（场景 B）
+ 打开**业务自己的**域名，例如：`https://sale.busyming.com/...`（不是 `fe-stack.busyming.com`）
+ HTML 里仍带有 `__APP_BASE__=/instance/p/...`，但浏览器 `pathname` **对不上**这个前缀
+ 代码走 env 回退 → 用**已有** `VITE_APP_BASE_NAME`（根路径多为 `/`；子路径如 `/subapp/xxx`）
+ **禁止改动 `.env*` 里的 `VITE_APP_BASE_NAME`**；不一致先人工确认

两种落地：

1. **网关直连（B1，新业务优先）**  
   请求到网关，网关把路由打到 instance。域名没有过多存量业务时用这套。运维配网关即可，**业务仓 Dockerfile/nginx 不动**。流水线用「新架构-前端统一发布模板」。

2. **nginx + Docker（B2，已投产）**  
   完全沿用以前的访问方式。流水线用「新架构-前端统一发布模板-nginx」，并按上文改 `Dockerfile` + `nginx-default.conf`。

###### 修改示例
```typescript
/** 去掉尾斜杠，保证以 / 开头；空或 ./ 视为根路径 */
function normalize(base?: string) {
 const value = String(base || '').trim().replace(/\/+$/, '')
 if (!value || value === '.' || value === './')
 return '/'
 return value.startsWith('/') ? value : `/${value}`
}

function isPathUnderBase(pathname: string, base: string) {
 if (base === '/')
 return true
 return pathname === base || pathname.startsWith(`${base}/`)
}

/**
 * 兼容两种访问方式：
 * 1. 场景 A（平台域名）：URL 仍在注入的 __APP_BASE__ 下 → 用注入值
 * 2. 自定义域名（网关或 nginx）：pathname 对不上注入值 → 用 VITE_APP_BASE_NAME
 */
export function resolveAppBaseName() {
 const injected = normalize(window.__APP_BASE__)
 const envBase = normalize(import.meta.env.VITE_APP_BASE_NAME || '/')

 if (injected !== '/' && isPathUnderBase(window.location.pathname, injected))
 return injected

 return envBase
}

export const appBaseName = resolveAppBaseName()

export function withAppBaseName(path = '/') {
 if (/^(?:[a-z]+:)?\/\//i.test(path))
 return path

 const base = appBaseName
 const p = path.startsWith('/') ? path : `/${path}`
 if (base === '/' || p === base || p.startsWith(`${base}/`))
 return p
 return `${base}${p}`
}

export function toAbsoluteAppUrl(path = '/') {
 return new URL(withAppBaseName(path), window.location.origin).toString()
}
```

```typescript
import { createRouter, createWebHistory } from 'vue-router'
import { resolveAppBaseName } from '@/utils/app-base'

const router = createRouter({
 history: createWebHistory(resolveAppBaseName()),
 routes,
})
```

```typescript
interface Window {
 /** History 路由 base（发布平台按访问路径注入） */
 __APP_BASE__?: string
}
```

#### 发布测试
完成以上改造后本地测试没问题即可推送代码至云效，并且在云效中运行流水线。流水线运行完成后回到平台（研发运维平台 `https://idp.busyming.com` 中的 `前端发布平台`）找到`版本管理`，**先用页顶环境条切到对应环境**，此时这里应该会出现刚才云效构建的版本。

版本展示规则：

+ 版本别名默认类似 `vyy.mm_dd.hh_mm`，可在详情中修改备注/别名
+ 版本号是别名后的 `#` 五位字符（如 `#mcni0`），用于访问指定版本、配置拉取；URL 显式带版本号时会固定该版本（不再走灰度匹配）
+ 构建成功只表示新版本入库，**不会**自动变成用户看到的那一版
+ 用户打开不带版本号的地址时：Web 看 **当前发布**，App 看 **默认分发**
+ **自动发版**（App 叫自动分发）：项目详情 → **构建 Webhook** 里按环境打开后，每次构建成功会把新版本设为当前发布 / 默认分发。dev～pre 可开；**生产不能开**，须人手点「发布版本」或「默认分发」
+ 开关没开：新版本只在列表里，需手动点发布；该环境**第一个成功版本**即使没开开关也会成为当前发布（App 的 Android / iOS 各算第一次）
+ 构建通知只推机器人消息，**不会**改当前发布；与自动发版是两个开关

### 灰度发布
用于把部分流量切到尚未全量发布的版本，适合内测、门店试点、按比例放量。

#### 配置灰度
1. 进入`版本管理`，选择目标项目
2. 对**构建成功**的版本打开「灰度配置」
3. 选择灰度类型并填写规则后提交；规则默认启用，可随时停用或删除

【截图：版本管理 - 灰度配置弹窗】

支持三种类型：

| 类型 | 含义 | 怎么填 |
| --- | --- | --- |
| 用户 ID 匹配 | 指定用户走该版本 | 用户 ID 列表 |
| 门店编码匹配 | 指定门店走该版本 | 门店编码列表 |
| 百分比匹配 | 按用户 ID 稳定分桶 | 1–99 的百分比 |


说明：

+ 同一个项目可对多个版本配灰度；访问时按规则顺序，**命中第一条即生效**
+ 未命中任何灰度时，仍走当前发布版本
+ URL 路径里已经带了五位版本号时，会**固定访问该版本**，不再走灰度匹配（与灰度命中无关的「显式订版本」）

#### 灰度如何生效
访问默认地址（不带版本号）时，平台会读取：

+ Header：`gray-third-userid` / `gray-store-code`
+ 或 Query：`userId` / `storeCode`

命中后**不 302、不改地址栏、不钉版本**：在当次请求里直接渲染对应灰度版本的 HTML（响应头可带灰度信息，便于排查）。刷新默认地址会重新匹配规则；未再命中则回到当前发布版。业务侧一般由网关/门户注入 Header；本地联调可临时在 URL 上拼 `?userId=xxx` 或 `?storeCode=xxx`。

### 资源管理
平台提供项目级图床，资源上传到 OSS 后通过 **CDN** 地址引用。凭证与列表里的访问根字段统一为 **`cdnDomain`**（无末尾 `/`），拼法：`cdnDomain + '/' + objectKey`。**不要再用已废弃的 `cdnBaseUrl`。**

**操作路径**：研发运维平台（`https://idp.busyming.com`）→ **前端发布平台** → 菜单 **资源管理** → 选择项目（项目编码 = 云效应用名）→ 新建文件夹 / 上传 → 复制 CDN 地址到业务代码。

**为什么不要继续把大图 / 字体等堆在业务仓 `assets/` 再打进版本包？**

| 问题 | 怎么做 |
| --- | --- |
| 每次构建 tar 重复占 OSS | 上传到图床后**删除仓内 assets** |
| 难单独 CDN 加速 | 列表复制 **CDN 地址**，项目中改引用 |
| 多环境难统一管理 | 图床跨环境共享，走「资源管理」规范管理 |

接入改造时若发现本地 `src/assets`（等）已有静态文件：**上传到本图床 → 代码填写 CDN 地址 → 删除仓内对应文件**（避免每次构建 tar 重复占 OSS）。也可让 Skill `upload-assets` 批量做。

1. 打开菜单`资源管理`
2. 选择项目（需具备资源查看/上传权限）
3. 可新建文件夹、上传文件、批量删除；支持拖拽上传

【截图：资源管理 - 目录与上传】

上传后的文件会落在 `{projectCode}/assets/...` 下，列表会给出 CDN 地址，可直接复制到业务里使用。

#### CDN 图片处理（使用规范）
列表缩略图、头像、Banner 不要直接用原图，按展示大小走 CDN 裁剪。参数写在 CDN URL 后：`?image_process=...`（**不是** OSS 的 `x-oss-process`）。

具体「这个场景该用多宽、裁不裁、质量多少」，不必死记参数：打开 **资源管理**，找到那张图，点资源右侧的 **处理**，在预览里试不同效果，满意后再复制带参数的地址到代码里。

常用示例（也可在「处理」里对照）：

| 场景 | 参数示例 |
| --- | --- |
| 列表缩略 | `?image_process=resize,w_240/format,webp/quality,Q_75` |
| 头像方图 | `?image_process=resize,s_100/crop,mid,w_100,h_100/format,webp/quality,Q_75` |
| H5 内容图 | `?image_process=resize,w_750/format,webp/quality,Q_85` |

完整示例：

`https://{cdnDomain}/{projectCode}/assets/icons/a.png?image_process=resize,w_240/format,webp/quality,Q_75`

说明：CDN **不支持** OSS 的 `m_fill` / `m_lfit`；`quality` 的 `Q_`/`q_` 须为 5 的倍数；场景优先用绝对质量 `Q_`。仅下载原图、打印、设计稿等才用无处理参数的原图 URL。

#### 图床稳定路径（推荐业务仓 assets 迁移）
管理端图床凭证开放整个 `{projectCode}/assets/` 目录，**相对路径可保持与本地 `src/assets` 一致**，便于把本地静态资源迁到 CDN 并改代码引用。须按本规范：`getGalleryToken` → OSS put → `register`（建议带 md5）；勿自造路径或跳过登记。

对接时**业务侧只需提供 `projectCode`（云效应用名）**：

1. `POST /stack-service/resource/getGalleryToken`，body：`{ "projectCode": "<云效应用名>" }`
2. 用返回的 STS 凭证上传到 `{baseDir}/{relativePath}`（即 `{projectCode}/assets/{relativePath}`）；响应里的访问根字段为 **`cdnDomain`**
3. `POST /stack-service/resource/register`，body：`{ "projectCode", "source": "manage", "files": [{ "filePath", "fileName", "fileSize?", "mimeType?", "md5?" }] }`
   `filePath` 为相对 `assets/` 的路径（不要带 `projectCode/assets` 前缀）；嵌套路径会自动补齐父目录；建议传文件内容 `md5`（32 位小写 hex）
4. 以 register 返回的 `cdnUrl` / `ossKey` 为准写入业务代码（无 `cdnUrl` 时用 `cdnDomain + '/' + ossKey`）；同名路径策略见项目 `resourceUpload.overwrite`（注意 CDN 缓存）
5. 写入业务时按上一节「CDN 图片处理」加 `?image_process=`，勿一律贴原图

权限：调用方需具备该项目的`上传资源`（`resourceUpload`）权限；请求头通常还需门户鉴权，以及管理端资源码 `permissionCode: feStackManageStatic`（以实际网关约定为准）。

增量建议：upload-assets 默认把清单写在业务仓 `node_modules/.fe-stack-upload/manifest.{env}.json`（按内容 sha256 跳过未变更）；**不要**在仓库根落 `.fe-stack-assets*.json`。

#### 业务运行时直传（按日目录）
业务系统若要自己直传（不经过管理端页面），可调节点服务：

1. `POST /instance/resource/getSTSToken`，body：`{ "projectCode": "xxx" }`，拿到**当天目录**的临时凭证（`{projectCode}/assets/YYYYMMDD/...`），响应含 **`cdnDomain`**
2. 用 STS 上传到返回的 `baseDir`
3. `POST /instance/resource/register` 登记入库（可批量 `files[]`，含可选 `md5`；`projectCode`）

注意：按日目录的 CDN 路径含日期，**不适合**「本地 assets 长期映射到固定 CDN 地址」这类迁移；迁移场景请用上一节图床稳定路径。Header 须带 **`x-api-key`**（`security.resourceApiKey`）。

#### API 调用
POST `https://fe-stack.busyming.com/instance/vercfg`（全环境同一主机，**不再**使用 `{env}-fe-stack` 分域）。

按 accessKey 拉取版本配置。`accessKey` 在平台`版本管理 → 详情 → 配置拉取凭证`中查看（先切到对应环境）。即便不传 `version`、只拉已发布版本配置，也需要带上**当前发布版本**对应的 `accessKey`。

如果发现 `accessKey` 泄露，请第一时间在对应版本详情中「重置凭证」。`凭证重置即时生效`，操作前请确认不会影响业务。

重置逻辑：会重置**当前版本以及创建时间不早于它的后续版本**；更早的历史版本不受影响。之后新发版会继续从已发布源继承这把新 key。例如：a 版本 10:00 创建，b 版本 10:01 创建，c 版本 11:00 创建——重置 a 时 b、c 一并重置；只重置 c 时仅影响 c。

**Body**

```json
{
 "projectCode": "xxx",
 "version": "a1b2c",
 "env": "prod"
}
```

`version` 可选；不传则取该 `env` 下当前已发布版本。`env` 建议显式传入（`dev` / `test` / `uat` / `pre` / `prod`）；缺省按生产处理。须与发版环境一致。

**Header**：`x-vercfg-key`（与版本 `accessKey` 一致）

**返回 **`data`

```json
{
 "success": true,
 "code": 200,
 "message": "ok",
 "data": {
 "projectCode": "",
 "versionName": "",
 "config": {}
 },
 "traceId": "c273de02c09e45a49e301d9fe6f6b5d3"
}
```

### 其他注意事项
下列事项**不在平台代码改造白名单内**，也**不是每个业务都必须做**。请按访问方案对照：A 平台直连、B1 网关直连、B2 nginx、C 容器嵌入（可组合）。无关项可跳过；尤其 §1 仅场景含 C 才做。

#### 1. 企微 / 微信 / 微信小程序（**仅场景 C**）
+ **仅当**页面会嵌进企微工作台、微信内置浏览器、小程序 webview 等容器时，才需要改：业务域名白名单、OAuth / 登录回调、JS 安全域名、webview 可打开域名列表
  - 走 fe-stack 直连 → 配 `fe-stack.busyming.com`
  - 走自定义域（B1 网关或 B2 nginx）→ 配真实业务域
+ 纯平台直连、纯业务域且**不**进上述容器 → **跳过本条**，不要当成必改项
+ **域名校验（仅 fe-stack 主机）**：研发运维平台（`https://idp.busyming.com`）→ 前端发布平台 → **实用工具 → 域名校验**，上传 `.txt`，有效期 **7 天**。文件只挂在 `https://fe-stack.busyming.com/{文件名}.txt` 或 `https://{env}-fe-stack.busyming.com/{文件名}.txt`。企微 / 小程序按**完整主机名**校验：白名单若是 `sale.busyming.com` 这类业务域，本工具帮不上，须在该业务主机根目录自行放文件（顶级域相同也不算）
+ 漏改常见现象：小程序里打不开 H5、授权失败、回调跳回旧域、JSSDK `invalid url domain`、校验文件 404
+ 若登录回调、扫码使用 `location.origin` 或写死旧域名/路径，切流后须同步改配置与代码
+ 责任方：业务自行上传校验文件 + 小程序 / 企微管理员配白名单（评估仅在场景含 C 时点名）

#### 2. 入口系统
+ 入口：场景 A 改为 fe-stack **生产**地址；场景 B 保留业务域（B1 配网关路由，B2 用 nginx 反代）
+ 小程序 webview / 消息卡片打开地址：按实际访问域配置（含 C 时同步 §1）
+ 责任方：业务 / 门户配置

#### 3. 网关 CORS 与 Cookie
+ 页面 Origin 变为 `https://fe-stack.busyming.com` 或新业务域后，若 API 为绝对网关地址且 `withCredentials: true`，须把新 Origin 加入网关 CORS 白名单
+ WebView / 第三方 Cookie、SameSite 策略可能更严，需联调验证（尤其场景含 C）
+ 责任方：网关 / 后端

#### 4. 同域 API 反代
+ 若生产 API 依赖「页面同域 + 业务容器内反代」，切到平台托管后必须改为网关绝对地址（或平台提供的 BFF）；与是否删除仓内 nginx 文件无关
+ 仅本地 Vite `server.proxy`、生产已是绝对网关 → 一般无阻断
+ 无法改为直连网关 → 不能仅靠本手册闭环上线

#### 5. 流水线与构建脚本
+ 约定：`pnpm/npm run build:${env}`，产物目录 `dist/`，上传 `{projectCode}/build/{DATETIME}.tar.gz`，回调 `https://fe-stack.busyming.com/instance/webhook/build`（body 带 `ENV`）
+ `CI_SOURCE_NAME` 必须等于平台 `projectCode`（云效应用名）
+ 仓库只有 `build:test` 等别名、或 env 名与流水线变量不一致时，先与运维对齐，勿擅自改构建语义
+ 平台直连或自定义域网关直连 →「新架构-前端统一发布模板」；已投产保留旧路径 →「新架构-前端统一发布模板-nginx」

#### 6. 健康检查与编排
+ 业务容器下线后，原 `/health`、`/health/check` 不再存在；确认 K8s / SLB 探针已摘掉旧服务
+ 责任方：运维

#### 7. 安全响应头
+ 原业务 Nginx 上的 `X-Frame-Options`、CSP 等不会随镜像带走；嵌入企微 / 小程序时确认平台或 CDN 侧头是否足够
+ 不建议在业务 HTML 里私自复制一整套头，除非有明确需求

#### 8. 自定义域名时补充（场景 B）
+ 地址栏路径 ≠ 注入的 `__APP_BASE__` 时，回退使用**已有** `VITE_APP_BASE_NAME`（应等于浏览器可见前缀）
+ **禁止**为接入平台去改 `.env*` 中的 `VITE_APP_BASE_NAME`；不一致时先核对/问业务方，勿擅自改写
+ **B1 网关直连**：运维在网关把该域名路由打到 instance；业务仓不改 Dockerfile/nginx
+ **B2 nginx**：按「流水线改造」改 Dockerfile + nginx-default.conf
+ 不要混用「始终信注入」与「始终信 env」，否则易出现路径多一截或 404
+ 若同时是场景 C：白名单 / 回调必须是业务域名本身，不要误配成 fe-stack 平台域

#### 9. 业务仓 Nginx / Dockerfile
+ **A / B1**：默认留原处，不必改、不必删
+ **B2**：必须改 `Dockerfile`（`ARG ENV` + sed）与 `nginx-default.conf`（`proxy_pass` 到 fe-stack）

#### 10. 静态资源迁 CDN（发现本地 assets 则应做）
+ 本地 assets 仍进版本包：每次构建 tar **重复占 OSS**、难单独 CDN
+ 应走：研发运维平台（`https://idp.busyming.com`）→ **前端发布平台** → **资源管理**；上传后**项目中填写 CDN 地址**，并**删除仓内 assets**
+ 访问根字段用 **`cdnDomain`**（勿再用 `cdnBaseUrl`）
+ 展示图勿一律原图：到资源管理点资源右侧 **处理** 预览后复制带 `?image_process=` 的地址；示例见上文「CDN 图片处理」
+ 批量迁移按上文「图床稳定路径」；`register` 建议带 md5
+ `import` 改 CDN 字符串可能影响打包管线，需按文件评估；确认引用切完再删本地文件

#### 11. 密钥
+ `.env*`、企微 secret、OSS 密钥等勿写入文档、评估报告或 git；示例一律打码
