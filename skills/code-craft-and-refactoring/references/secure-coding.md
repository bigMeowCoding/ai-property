# 安全代码参考

安全评审从资产、信任边界和数据流出发，而不是从危险 API 清单出发。

## 五项原则

1. 清楚接口真正承诺的行为，不依赖未定义行为。
2. 跨越信任边界的数据默认不可信。
3. 只授予完成任务所需的最小权限。
4. 减少外部入口、可变状态、可扩展点和敏感数据暴露面。
5. 用独立防线做纵深防御，避免单点失守。

## 威胁与数据流检查

对每个入口回答：

- 数据最初来自哪里，经过哪些解析、转换、存储和输出？
- 结构、长度、范围、编码、类型和业务约束在哪里校验？校验后是否还能被修改？
- 身份认证与授权分别在哪里发生，是否存在对象级/租户级越权？
- 哪些日志、异常、缓存、序列化对象和响应会携带敏感信息？
- 数值计算是否可能溢出、下溢、截断或导致过量资源分配？
- 外部调用、文件、模板、查询和命令是否存在注入或路径操控？
- 重试、并发和检查后使用是否产生竞态、重复执行或 TOCTOU？

## 高风险领域

| 领域 | 检查与处理方向 |
|---|---|
| 外部输入 | 先验证结构与范围，再分配资源、查询或执行 |
| 授权 | 默认拒绝；在服务端和对象边界再次校验；避免只靠 UI 隐藏 |
| 敏感信息 | 最小收集、最小保留；净化日志/异常；必要时加密并限制访问 |
| 整数与尺寸 | 使用安全运算或前置边界检查；同时防范内存/磁盘耗尽 |
| 序列化 | 不反序列化不可信原生对象；采用明确 schema、类型白名单、签名/加密 |
| 可变数据 | 防御性拷贝或不可变封装；检查浅拷贝、别名和竞态 |
| 继承/扩展点 | 安全敏感能力优先封闭或委托；新增入口不能绕过旧授权 |
| 密钥与令牌 | 不写入源码、日志和错误；限制权限、轮换并处理吊销 |
| 依赖 | 使用受支持和已修复版本；评估供应链、锁文件与更新响应流程 |

## 安全缺陷优先级

按用户影响的**严重性 × 发生可能性**排序，并考虑公开关注、重要客户、关键业务和现有缓解措施：

- 高严重性、高可能性：立即处理。
- 高严重性或高可能性之一成立：优先处理并限制暴露。
- 低严重性、低可能性：记录、安排或接受风险。

安全、权限绕过、敏感数据泄漏和数据破坏通常至少属于高优先级候选。不要在普通评审渠道公开可被直接利用的细节；只向需要知情的人提供最小必要信息。

## 风险应对设计

- **双引擎**：关键能力保留两种被持续演练的可切换方案，避免备用路径腐化。
- **降落伞**：提前部署可配置、可回滚、可审计的应急开关或降级策略。
- **纵深防御**：沿攻击路径布置相互独立的校验、授权、隔离、监控和响应机制。

这些设计会增加复杂度，只用于失败代价足够高的关键风险点，并且必须实际演练。

## 安全验证

- 为攻击路径、越权、边界值和失败清理增加负向测试。
- 使用静态分析、依赖扫描和动态测试补充人工数据流审查。
- 验证修复不能只证明“危险输入被拒绝”，还要证明正常兼容路径未被破坏。
- 明确已验证、仅推断和未覆盖的攻击面。
