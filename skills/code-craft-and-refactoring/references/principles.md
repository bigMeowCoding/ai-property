# 代码精进核心原则

## 质量模型

优秀代码同时追求三种经济性：

- **经济**：在软件全生命周期内，用更少的人力、时间和计算资源产生更大价值。
- **规范**：通过共同约定降低理解、评审、测试和维护成本。
- **安全**：把不可承受的威胁、数据损坏和权限风险控制在可接受范围。

“最适合当前环境”比抽象完美更重要。创业项目、成熟基础设施和安全关键系统的质量门槛不同；判断必须结合用户影响、生命周期和失败成本。

## 三层规则

不要把所有建议当成同等强度：

1. **行为不变量**：正确性、数据完整性、安全边界、公共接口承诺。违反即是缺陷。
2. **团队约定**：命名、格式、目录、异常与测试策略。优先遵循仓库现状和明确规范。
3. **经验启发**：函数长度、类大小、某种设计模式等。用于提示调查，不用于机械判错。

## 质量流水线

依靠制度和快速反馈降低个人失误：

1. **程序员**：理解问题、保持代码清晰、主动验证假设。
2. **编译器/类型系统**：认真处理警告，不轻率压制。
3. **回归测试**：覆盖关键行为、边界和失败路径。
4. **代码评审**：用更多视角发现盲区并传播知识。
5. **静态分析**：常态化检查可自动识别的问题。

反馈应尽量左移：能在需求或接口层排除的问题，不要等到生产环境才发现。

## 核心决策问题

每次任务先回答：

1. 用户真正要解决的问题和完成标准是什么？
2. 这是新功能、缺陷修复、重构、性能优化还是安全加固？是否混戴了帽子？
3. 哪些可观察行为、接口、数据和兼容性必须保持？
4. 最大风险来自可读性、设计、正确性、性能还是安全？
5. 有什么自动化测试或可复现证据作为安全网？
6. 最小、最容易验证的下一步是什么？

## 常见误区

| 误区 | 纠正 |
|---|---|
| 重构就是让代码漂亮 | 重构为降低未来修改成本，并保持外部行为 |
| 大批量改完再统一测试 | 小步修改，每步获得反馈 |
| 测试通过就证明需求正确 | 测试只证明被表达出来的行为；还要核对真实业务闭环 |
| 覆盖率高就等于测试好 | 覆盖率只能发现未覆盖代码，不能证明断言质量 |
| 性能凭经验优化 | 先定义指标、建立基准、定位热点，再对比结果 |
| 安全就是输入校验 | 还要覆盖授权、敏感信息、数据流、攻击面与纵深防御 |
| 规范是普适硬规则 | 区分行为不变量、团队约定和经验启发 |
| 抽象越多越可扩展 | 只为已知变化建立最简单的合适边界 |
| 运行良好的丑代码必须立刻清理 | 没有现实收益时不必制造变更风险 |

## 实践口诀

- 优秀代码首先要让下一位维护者看懂。
- 先理解行为，再改变结构。
- 先让测试变绿，再戴上重构帽子。
- 跨越信任边界的数据默认不可信。
- 简单直观通常更经济，但关键风险点允许有意识地增加防御层。
- 没有测量，不宣布性能提升；没有复现，不宣布缺陷已证实。
