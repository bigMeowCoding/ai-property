# 代码评审工作流

评审目标是发现会伤害用户、数据、权限、兼容性或维护效率的具体问题。不要把风格清单当作机械打分表。

## 1. 对齐评审基线

- 明确评审对象：工作区、提交、分支差异或 PR。
- 阅读任务描述、验收条件、仓库规则和测试说明。
- 先看 diff 统计与文件角色，再逐块读变更；不要把 rename、移动和行为修改混为一谈。
- 检查用户已有的无关改动，避免把它们误归因于本次变更。

## 2. 走查业务闭环

从用户操作或外部入口开始，沿路径检查：

`入口 → 参数/事件 → 控制器或组件 → 领域状态 → 持久化/Worker/外部服务 → 结果呈现或响应`

重点确认：

- 新代码是否真的可达，条件是否可能永远不成立。
- 状态是否写到正确来源，并被所有消费者看到。
- 主线程、Worker、服务端/客户端或同步/异步实现是否保持对称。
- 错误、取消、超时、重试、空数据和重复操作是否闭环。
- 并发回调、循环、定时器、动画帧或订阅是否可能重入和叠加。

## 3. 四维风险检查

### 正确性与规范

- 是否满足明确需求、边界条件和公共接口合约？
- 命名与结构是否准确表达行为，还是隐藏副作用或单位？
- 异常是否保留原因、避免吞错，并在所有路径清理资源？
- 文档、示例、配置和类型是否与行为同步？

### 经济与性能

- 是否实现了不需要的需求或新增无收益抽象？
- 热路径是否出现无界增长、重复 I/O、N+1、频繁分配/拷贝或长锁？
- 性能结论是否有基准、profile 或复杂度证据？
- 缓存、异步、并发和延迟初始化是否引入更大的生命周期或一致性成本？

### 安全与数据

- 外部数据是否沿完整路径被校验、编码和授权？
- 是否存在对象级越权、敏感信息泄漏、注入、路径操控或整数边界问题？
- 可变共享数据、序列化、日志、异常和依赖更新是否扩大攻击面？
- 数据迁移、回滚、幂等和部分失败是否保护数据完整性？

### 重构与回归

- 变更是否保持应保持的可观察行为？
- 是否混合了功能、重构、格式化和依赖升级，导致难以审查？
- 新测试是否会在缺陷存在时失败，还是只执行代码？
- 是否有明显坏味道导致本次需求难以实现；最小预备性重构是什么？

## 4. 验证

- 优先运行最小相关测试或复现路径，再按风险扩大到模块/集成/端到端测试。
- 适用时运行类型检查、lint、编译、静态分析、基准或安全扫描。
- 禁止仅凭“看起来没问题”写“逻辑正确”或 LGTM。
- 无法运行的验证要写明原因和剩余风险。

## 5. 发现格式

只报告独立、可操作、有证据的问题。每条发现包含：

1. **优先级**：按用户影响严重性与发生可能性评估。
2. **位置**：最小相关文件与行。
3. **触发条件**：什么输入、状态或时序会出现。
4. **影响**：用户、数据、安全、兼容性或维护成本如何受损。
5. **证据**：调用链、状态流、测试结果或可复现行为。
6. **修复方向**：最小可行建议，不强行展开无关重写。

优先级参考：

- **P0**：普遍发生的灾难性问题，阻断发布或运行。
- **P1**：高影响且现实可触发，应在合并前修复。
- **P2**：中等影响或有限条件下触发，应尽快修复。
- **P3**：低影响但明确可操作，不作为阻断项。

如果没有发现，明确说“未发现可操作缺陷”，同时列出实际检查和未覆盖范围；不要用“没有发现”冒充“证明无缺陷”。
