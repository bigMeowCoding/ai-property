# 规范代码参考

规范的目标是降低理解和协作成本。先服从仓库已有 formatter、lint、语言指南和团队约定；以下内容用于补充缺失规则，不用于覆盖现状。

## 可读性与分块

- 让每个函数、代码块和文件围绕一个清晰目标组织。
- 用命名、缩进、空行和靠左对齐呈现逻辑层级，减少读者工作记忆负担。
- 每行尽量表达一个行为；复杂表达式按语义边界换行。
- “基础块不宜超过约 25 行”只是调查信号：超过时检查是否混合职责，不要机械拆分完整逻辑。
- 先保持与相邻代码一致；大规模格式化不要混入功能 diff。

## 命名与声明

- 名称要准确表达领域含义，避免模糊缩写、误导单位、隐藏副作用和重复上下文。
- 同一概念使用同一词汇；同一词汇不要表示多个概念。
- 布尔值表达可判断的事实；函数名揭示主要动作和副作用。
- 局部变量在接近使用处声明并尽量初始化；长生命周期状态集中管理并限制可变入口。
- 改名先搜索定义、调用点、序列化键、配置、反射和外部接口，避免只改编译期可见位置。

语言命名风格是团队约定。例如 Java 常用类名大驼峰、方法/变量小驼峰、常量大写下划线；其他语言服从其生态和仓库规则。

## 函数与接口

- 从调用者视角说明功能、参数、返回值、边界、错误和副作用。
- 外部接口要少、要小、成文、清楚、稳定；没有明文承诺的行为不能被调用者依赖。
- 一次读取、一次网络调用或一次迭代不一定完成整个业务动作；遵守协议规定的部分结果语义。
- 把外部接口与内部实现隔离，允许内部演进而不破坏调用方。
- 变更公共接口前检查所有调用方、兼容策略、弃用路径和文档；不要静默改变语义。

## 异常与失败

- 异常只表达异常状况，不用作普通分支或预期业务结果。
- 在最能补充上下文或恢复的位置捕获；捕获精确类型，不吞异常。
- 转换异常时保留原始原因，并提供对调用者有用且不泄密的上下文。
- 区分可恢复错误、调用方错误和系统故障；让接口明确失败模型。
- 清理资源使用语言提供的确定性机制，如 `defer`、上下文管理器、RAII、try-with-resources 或 `finally`。

## 注释与文档

- 注释解释“为什么、约束、权衡和非显然风险”，不要逐行复述代码。
- 优先通过命名和提炼函数让代码自我表达；大量解释性注释是重构信号。
- 注释必须准确、必要、清晰，并与代码一起更新。
- 注释语言服从团队约定；不要把“必须英文”当成跨项目硬规则。
- 公共 API 文档与用户指南要和源代码同步，示例应可运行。

## 文件组织

- 目录按用户和维护者理解问题的方式组织，而不是按偶然实现细节堆放。
- README 说明用途和入口，LICENSE 说明许可，`src` 承载实现，`test` 承载验证，`docs` 承载使用与设计；具体名称服从生态。
- 一个文件中相关内容相邻、层次稳定；拆文件要带来更清晰的职责或依赖边界。

## 规范检查

把问题分级：

- **缺陷**：违反行为、接口、安全或数据不变量。
- **约定偏差**：违反明确 formatter、lint、仓库或团队规范。
- **可读性建议**：有具体理解成本和改进收益。
- **个人偏好**：无可证明收益时不要作为阻塞意见。
