## 7. 任务拆分与并行计划（Task Breakdown）

### 7.1 拆分原则

- **核心先行**：先完成最小可用版本（MVP），确保 API 契约稳定
- **测试并行**：核心逻辑开发的同时，测试用例可以同步编写
- **2 个 Agent 并行**：一个负责核心实现，一个负责测试 + 文档 + 工程化

### 7.2 任务卡片（Task Cards）

#### 模块 A：核心实现（Agent-1 负责）

| 任务 ID | 任务名称 | 类型 | 输入 | 输出 | 依赖 | 验收点 |
|---------|----------|------|------|------|------|--------|
| T-A1 | 核心算法/逻辑实现 | core | Spec API 设计 | 主入口文件 + 类型定义 | 无 | 所有公开 API 有实现，通过基础用例 |
| T-A2 | 错误处理与边界 | core | 错误契约定义 | 错误类定义 + 边界处理逻辑 | T-A1 | 所有错误类型可被正确 catch 和识别 |
| T-A3 | 性能优化（如需） | core | 基准测试数据 | 优化后的实现 | T-A1 | 性能指标达标 |

> **模块 A 交付物：** 可运行的核心库代码  
> **并行条件：** T-A1 完成后，模块 B 启动

---

#### 模块 B：测试与工程化（Agent-2 负责）

| 任务 ID | 任务名称 | 类型 | 输入 | 输出 | 依赖 | 验收点 |
|---------|----------|------|------|------|------|--------|
| T-B1 | 单元测试用例 | test | Spec API 设计 + 错误契约 | 测试文件（覆盖率 ≥ 90%） | T-A1 | 所有公开 API 有测试，边界值覆盖 |
| T-B2 | 基准测试 | test | 核心实现 | benchmark 脚本 + 报告 | T-A1 | 可复现性能数据 |
| T-B3 | 使用文档 + README | docs | 所有使用示例 | README.md + CHANGELOG.md | T-A1, T-B1 | 新用户 5 分钟可上手 |
| T-B4 | 打包与发布配置 | infra | 核心实现 | rollup/vite 配置 + CI 脚本 | T-A1 | 可产出 esm/cjs/umd 三种格式 |

> **模块 B 交付物：** 完整测试 + 文档 + 工程化配置  
> **并行条件：** 依赖模块 A 的 T-A1 完成后启动，与 T-A2/T-A3 可部分并行

## 8. 验收注意点与重点场景（Acceptance Checklist）

### 8.1 必验场景（Must Verify）

| 优先级 | 场景 | 验证方式 | 通过标准 |
|--------|------|----------|----------|
| 🔴 P0 | 所有公开 API 正常调用 | 代码执行 | 返回值符合类型定义 |
| 🔴 P0 | 参数非法时正确抛错 | 代码执行 | 抛出对应错误类型，信息清晰 |
| 🔴 P0 | 边界值处理正确 | 代码执行 | 空值、极值、异常输入不崩溃 |
| 🟡 P1 | 性能指标达标 | benchmark | 执行耗时在目标范围内 |
| 🟡 P1 | 包体积达标 | 分析工具 | gzip 后体积在目标范围内 |
| 🟢 P2 | 文档完整性 | 人工阅读 | 基础/高级/错误处理示例齐全 |

### 8.2 易遗漏场景（Easy to Miss）

| 风险点 | 为什么容易漏 | 验收方法 |
|--------|--------------|----------|
| 内存泄漏 | 定时器/事件未清理 | 长时间运行后检查内存占用 |
| 并发调用 | 同一函数并发执行 | 验证状态不互相污染 |
| 类型导出 | 忘记导出类型定义 | 在 TS 项目中引入验证类型推断 |
| 副作用隔离 | 修改全局状态 | 验证多次调用互不干扰 |

### 8.3 回归检查（Regression Check）

| 影响面 | 检查项 | 验证方式 |
|--------|--------|----------|
| 现有项目引用 | 升级后现有调用点是否报错 | 在 1-2 个现有项目中试升级 |
| 包体积 | 新增依赖是否显著增加体积 | 对比升级前后体积 |
