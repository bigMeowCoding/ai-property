## 交付物选择

| 需要解决的问题 | 最小交付物 |
|---|---|
| 解释一个决策 | ADR |
| 比较真实取舍 | 方案评审 |
| 设计新系统/重大调整 | 架构设计文档 + 核心图 |
| 统一实现方式 | 可执行技术规范 + 示例/门禁 |
| 存量改造 | 目标架构 + 分阶段迁移与回滚计划 |
| 审计 | 证据表 + 风险发现 + 行动计划 |

所有交付物都应标注状态：草案、已接受、实施中、已替代、已废弃。

## 方案评审

简单任务无需机械生成多方案。只有存在真实决策分歧时比较 2–3 个方案，并保留“维持现状/局部改进”基线。

```markdown
# {决策主题} 方案评审

## 1. 决策摘要
- 推荐：
- 适用范围：
- 决策截止/复核日期：

## 2. 业务目标与约束
- 用户/业务结果：
- Rank：
- 主要复杂度：
- 不可改变项：
- 未知项：

## 3. 现状证据
| ID | 事实/推断/未知 | 内容 | 来源/验证方式 |

## 4. 方案
### A. 维持现状或局部改进
- 4R 变化：
- 收益、代价、风险、可逆性：

### B. {方案}
...

## 5. 取舍
| 维度 | 优先级/约束 | A | B | C |
|---|---|---|---|---|

## 6. 推荐与反对理由
- 为什么现在选它：
- 为什么不选其他方案：
- 哪些新证据会改变决策：

## 7. 落地与验证
- 切片、owner、验收、灰度、回滚：
```

决策矩阵用于暴露取舍，不用任意权重生成伪精确总分。

## ADR

```markdown
# ADR-{编号}: {决策标题}

- 状态：提议 / 接受 / 已替代 / 已废弃
- 日期：YYYY-MM-DD
- Owner：
- 关联决策：

## 背景
业务目标、当前 Rank、主要复杂度、关键证据与约束。

## 决策
我们决定……

## 理由
为什么该方案最符合当前优先级；包含未选方案及理由。

## 后果
- 正面：
- 负面：
- 新增复杂度：
- 风险与缓解：

## 实施与验证
- 边界/契约变化：
- 迁移与回滚：
- 验收指标与基线：

## 复核触发点
何时需要重新评估本决策。
```

ADR 记录有长期影响、存在取舍的决策；普通实现细节不必全部写 ADR。

## 架构设计文档

```markdown
# {系统} 前端架构设计

## 1. 摘要
- 目标、范围、推荐方案、主要风险

## 2. 业务背景与约束
- 用户、核心流程、团队、时间、兼容、安全/合规、成本

## 3. 证据与主要复杂度
- 事实/推断/未知
- 当前最重要的 1–2 个复杂度及因果链

## 4. 现状与目标 4R
- Rank / Role / Relation / Rule
- 静态图 + 核心时序/状态图

## 5. 边界与契约
- 模块/包/应用/部署/团队边界
- 数据与状态所有权
- API/事件/错误/版本语义

## 6. 质量属性
- 性能、可用性、安全、可扩展、成本与可观测性
- 基线、预算和验证方法

## 7. 工程与交付
- 构建、测试、CI、制品、发布、灰度、回滚

## 8. 迁移计划
| 阶段 | 业务切片 | 依赖 | Owner | 验收 | 回滚 |

## 9. 风险、未知与演进触发点

## 10. ADR 与附录
```

## 可执行技术规范

规范必须回答“如何被发现和执行”：

| 规范领域 | 需要定义 | 可执行机制示例 |
|---|---|---|
| 包/模块 | 公开 API、依赖方向、循环依赖 | exports、lint、依赖图 |
| 状态/数据 | owner、更新入口、缓存失效、错误 | 类型、Schema、契约测试 |
| 组件 | API、状态、可访问性、主题 | 示例、组件测试、视觉回归 |
| 安全 | 信任边界、认证、CSP、敏感数据 | 扫描、review gate、运行时策略 |
| 性能 | 页面/人群、预算、测量方式 | CI budget、RUM 告警 |
| 发布 | flag、灰度、监控、回滚 | 流水线、runbook、演练 |

### 规范条目模板

```markdown
### {规则名称}
- 目的：保护什么风险或能力
- MUST / SHOULD / MAY：
- 适用范围与例外：
- 正例/反例：
- 自动检查：
- Owner 与升级路径：
- 废弃/迁移策略：
```

不要把某个团队的格式偏好写成普遍正确性规则。安全建议（如 Token 存储、CSP）必须结合威胁模型、后端能力和官方资料，不用一句绝对规则覆盖所有架构。

## 迁移与验收

### 迁移计划必须包含

- 目标、不变量、允许改变项和明确不做项；
- 按业务能力切片，而不是只按文件目录切片；
- 兼容层、双轨或 feature flag 的生命周期；
- 数据迁移、幂等、冲突与补偿；
- 每阶段 owner、进入/退出条件；
- 灰度、监控、回滚和旧路径清理。

### 验收证据

```markdown
## 验收
- 功能与兼容：测试/走查/契约结果
- 架构约束：依赖图、门禁、owner
- 质量指标：基线 → 结果，场景与样本
- 发布恢复：灰度和回滚演练
- 收口：旧代码、适配、flag、双写清理
- 未验证与剩余风险：
```

“功能无损、性能达标、监控正常”只有在附上范围、方法和结果时才算验收标准。
