## 工程决策原则

1. 从交付瓶颈和治理目标出发，不从工具排行榜出发。
2. 区分开发机、CI、生产构建和运行时指标；单一 HMR 数字不能代表总体收益。
3. 迁移前建立等价基线，迁移后比较同一工作负载。
4. 自动化规则要有 owner、误报处理和升级策略。
5. 工具消除的复杂度必须大于它新增的配置、运维和认知成本。

## 构建系统

### 先收集需求

- 应用、库还是混合仓库；
- CSR、SSR、SSG、边缘或多目标产物；
- 浏览器/Node/终端兼容范围；
- 插件、宏、代码生成和遗留 loader；
- 冷启动、增量构建、CI、内存和产物目标；
- source map、安全、签名与制品追溯。

### 选型维度

| 维度 | 需要验证 |
|---|---|
| 兼容性 | 框架官方支持、插件、测试、CSS、SSR、浏览器目标 |
| 性能 | 真实仓库的冷/热构建、CI、缓存命中、产物 |
| 可调试性 | source map、错误信息、分析工具、开发体验 |
| 可维护性 | 配置复杂度、团队经验、生态稳定性、升级路径 |
| 可逆性 | 并行运行、回退路径、制品差异 |

候选可能包括 Vite、Webpack/Rspack、框架自带构建、Rollup、esbuild 等，但不预设“多数项目首选”。框架集成和官方支持通常比孤立基准更重要。

### 构建性能闭环

```markdown
- 场景：冷启动 / 单文件修改 / 大范围修改 / CI 全量构建
- 环境：硬件、运行时、缓存状态
- 基线：中位数与波动范围
- 瓶颈：解析、转换、类型检查、插件、I/O、打包或上传
- 变更：
- 结果：同场景对比
- 回归：产物、source map、测试、兼容性
```

## Monorepo

### 适用信号

- 多应用共享代码且跨仓版本同步成本高；
- 需要原子变更和统一质量门禁；
- 依赖图可支持受影响构建与测试；
- 团队愿意共同治理工具链和包边界。

不适用信号：团队/合规要求强隔离、仓库体量与 CI 无治理能力、共享代码很少、所有应用生命周期完全不同。

### 分开设计五种边界

1. 仓库边界；
2. 包和源码边界；
3. 构建任务与缓存边界；
4. 发布/版本边界；
5. 团队所有权边界。

它们不必完全重合。`apps` 可组合 `packages` 是常见约束，但真实规则应按项目定义并自动验证。

### 治理清单

- 内部包公开 exports，禁止深层私有导入；
- 依赖方向和循环依赖有自动检查；
- 缓存 key 包含代码、配置、环境与工具版本；
- 明确统一版本、独立版本或锁步发布；
- 共享配置支持演进和例外，不成为隐式全局状态；
- 包有 owner、弃用和破坏性变更策略。

## 微前端

### 只有在这些问题真实存在时考虑

- 多团队需要独立发布且持续互相阻塞；
- 遗留技术栈需要分阶段替换；
- 业务边界稳定、运行时自治收益高；
- 已具备自动部署、监控、版本治理和故障隔离能力。

如果问题主要是源码组织、共享包或构建性能，先评估模块化/Monorepo。微前端新增运行时下载、共享依赖、路由、样式、通信、认证、观测和体验一致性成本。

### 必须定义的契约

- 应用发现与加载、超时、失败和降级；
- 路由与导航所有权；
- 身份、权限和会话边界；
- 共享依赖版本与隔离策略；
- 样式、DOM、全局事件和浏览器 API 约束；
- 跨应用事件/API 的 Schema、版本、幂等和错误语义；
- 独立发布、兼容窗口、回滚和联合演练。

实现可用 Module Federation、Web Components、框架容器或服务端组合等，方案由约束决定。

## 样式与设计系统

CSS Modules、原子化 CSS、原生 CSS、预处理器、零运行时 CSS-in-JS 等都是手段。选择时评估：

- Token 与主题是否需要跨应用/跨端共享；
- 样式隔离和覆盖模型；
- 动态样式、SSR、CSP 与运行时成本；
- 设计师/开发者工作流和调试体验；
- 遗留样式迁移和视觉回归能力。

设计系统不仅是组件库，还包括 Token、交互/可访问性规则、内容规范、版本治理、文档和支持机制。公共样式必须避免无 owner 的全局覆盖。

## 性能与可观测性

### 预算而非通用阈值

基于业务和用户环境为关键页面定义：

- 用户体验：LCP、INP、CLS 或业务自定义响应时间；
- 网络：初始/异步 JS、CSS、图片、字体、请求数；
- 主线程：长任务、脚本执行、渲染与内存；
- 服务端渲染：TTFB、流式分段、水合和缓存命中；
- 业务指标：转化、完成率、错误恢复和交互成功率。

阈值可参考 Web 标准或产品 SLO，但需注明来源、分位数、设备/网络和页面范围。

### 诊断顺序

1. 用真实用户监控确认受影响人群和页面；
2. 用实验室环境复现并建立基线；
3. 定位网络、主线程、渲染、水合、缓存或第三方瓶颈；
4. 做最小干预并同场景复测；
5. 在 CI 设预算，在生产观察分位数与业务影响。

不要默认手工分包、memo、预加载、SSR 或 Worker 一定改善性能；每项都有适用条件和副作用。

## 质量门禁

按风险组合：

- 快速反馈：格式、lint、类型、受影响单测；
- 契约：API Schema、包边界、事件与兼容测试；
- 用户行为：组件/集成/E2E、可访问性、视觉回归；
- 制品：可复现构建、依赖许可/漏洞、大小预算、source map；
- 发布：feature flag、灰度、RUM/错误监控、自动或人工回滚。

每个门禁要说明保护的风险、运行位置、失败责任人、例外流程和耗时预算。覆盖率数字不是单独的质量目标。
