## 从变化轴设计边界

不要从 Atomic Design 或固定目录模板开始。先回答：

- 什么会一起变化，什么应独立变化？
- 谁负责它，谁消费它，发布节奏是否一致？
- 业务规则属于哪个领域，数据的唯一 owner 是谁？
- 这个能力需要源码复用、构建期复用还是运行时独立？
- 出错时影响范围应多大？

高内聚边界应围绕稳定职责和共同变化，而不是围绕“components/hooks/utils”文件类型。

## 推荐的分层视角

一种可选模型：

```text
App / Page       路由、页面编排、跨域流程
Feature / Domain 业务能力、用例、领域规则
UI               无业务或轻业务的交互组件与设计 Token
Data / Service   API 契约、缓存、数据转换、持久化
Platform / Infra 路由、监控、配置、认证适配、构建运行时
```

这不是强制目录。项目可采用垂直切片，将一个业务域的 UI、状态、API 和测试放在一起。关键约束：

- 上层可以组合下层；下层不反向依赖具体业务；
- 跨域协作通过公开契约，不读取对方内部 store 或私有文件；
- 公共层必须有准入标准、owner 和稳定性承诺；
- 页面负责装配，不成为所有业务逻辑的最终归宿。

### 何时抽取共享能力

满足多数条件再抽取：

- 已有至少两个真实消费者，而不是预测复用；
- 语义一致，不只是 UI 看起来相似；
- 变化节奏和兼容要求可接受；
- 抽取后接口比复制更容易理解；
- 有 owner、测试和版本/发布策略。

共享越广，兼容成本越高。广泛使用不是自动健康信号。

## 状态与数据所有权

先分类，再选机制：

| 状态类型 | 默认 owner | 设计重点 |
|---|---|---|
| URL/导航状态 | 路由 | 可分享、前进后退、编码与兼容 |
| 局部 UI 状态 | 最近使用组件/Feature | 生命周期、重置与可测试性 |
| 表单/草稿 | 表单或领域用例 | 校验、脏状态、持久化与恢复 |
| 跨组件客户端状态 | 明确业务域 | 更新入口、订阅范围、并发 |
| 服务端状态 | 数据访问/缓存层 | 新鲜度、失效、重试、乐观更新 |
| 持久化状态 | 明确存储 owner | 版本迁移、隐私、过期与冲突 |

每份状态应有唯一权威来源。复制状态时说明同步方向、冲突策略和终止条件。不要用全局 store 掩盖边界问题，也不要因“prop drilling”层数达到某个数字就自动引入全局状态。

## 组件 API 与组合

### 先定义契约

组件 API 要说明：

- 输入的语义、默认值和受控/非受控模式；
- 事件发生时机、载荷和取消/错误语义；
- loading、empty、error、disabled 和权限状态；
- 可访问性、键盘和焦点责任；
- 样式/主题扩展点及兼容承诺。

### 组合优于配置的条件

组合、slots、children、compound components 适合：

- 子区域有独立变化和复用需求；
- 消费者需要控制结构或渲染；
- 配置对象已经承载大量互斥选项。

简单且稳定的组件使用少量 props 更清晰。不要把所有 API 都改成复合组件，也不要为了避免 props 就引入隐藏 Context。

### Headless 与视觉组件

- **Headless**：复用交互、状态机与可访问性，视觉由消费方控制；
- **视觉组件**：统一品牌、布局和交互，减少重复决策；
- **业务组件**：封装领域语义，不应伪装成跨项目通用组件。

选型由复用边界和变化轴决定。设计系统通常需要视觉组件与低层 primitives，而不是只有一种形态。

## 边界治理

可执行手段：

- package exports、TypeScript project references、workspace 依赖；
- ESLint/import 规则、依赖图和受影响构建；
- API Schema、事件类型、契约测试；
- CODEOWNERS、变更审批和弃用策略；
- 组件目录/Storybook 示例、视觉回归和可访问性测试。

边界审查清单：

- [ ] Rank 和业务域是否明确；
- [ ] 依赖方向是否单向、可验证；
- [ ] 状态和数据是否有唯一 owner；
- [ ] 跨域契约是否包含版本与错误语义；
- [ ] 共享能力是否有真实消费者和 owner；
- [ ] 核心状态与失败路径是否可测试；
- [ ] 变更能否在预期范围内发布和回滚。
