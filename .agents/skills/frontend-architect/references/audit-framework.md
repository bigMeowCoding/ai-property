# 前端架构审计框架

用于存量前端系统的证据驱动审计。目标不是给项目套一个“健康分”，而是找到影响业务、用户或团队的架构机制，给出可验证、可分阶段执行的改进路径。

## 审计原则

1. **先基准，后结论**：说明审计对象是某个 commit、工作区、环境、发布版本还是线上时段。
2. **先业务闭环，后目录清单**：至少走查一个核心用户流程，从入口追到数据、状态、错误和部署链路。
3. **事实、推断、未知分开**：不能访问线上监控时，不得写“错误率低”；没跑测试时，不得写“测试充分”。
4. **阈值来自上下文**：文件行数、依赖数、覆盖率、Bundle 大小和 Web Vitals 目标都应来自项目基线、产品目标或明确预算。行业值只能作参考。
5. **架构和代码分层**：跨模块边界、数据所有权、部署和团队协作属于架构；局部坏味道交给 `code-craft-and-refactoring`。
6. **优先级不是严重度别名**：严重问题若当前没有安全实施条件，也可能需要先做防护和测试，再安排结构调整。

## 审计准备

### 明确范围

- 业务范围：哪些用户、页面、流程和数据在内；
- 技术范围：仓库、包、应用、运行环境、浏览器与终端；
- 时间范围：当前快照、最近若干发布或某次事故；
- 输出范围：诊断、路线图、规范、图表，是否包含实施；
- 不可改变项：兼容性、发布窗口、公共 API、合规和预算。

### 建立证据表

| 编号 | 类型 | 证据 | 能支持的结论 | 局限 |
|---|---|---|---|---|
| E1 | 事实 | 文件/配置/命令/监控/事故记录 | 直接观察 | 时间与环境范围 |
| I1 | 推断 | E1 + E2 → 推断 | 假设性解释 | 置信度与反例 |
| U1 | 未知 | 缺少的日志、流量或需求 | 暂不能判断 | 验证方法与负责人 |

常用只读证据：仓库说明、锁文件、构建配置、路由入口、包依赖图、状态定义、API 契约、测试、CI、部署配置、监控与发布记录。命令和工具要服从仓库现状，不为审计强行安装依赖。

## 七阶段流程

### 阶段 1：目标、Rank 与主要复杂度

先回答：

- 当前讨论的是产品、系统、应用、模块还是组件层？
- 最重要的用户/业务结果是什么？
- 当前最主要的 1–2 个复杂度是什么？
- 症状是业务规模带来的，还是技术或组织方式放大的？

输出一个现状 4R：

```markdown
## 现状 4R
- Rank：
- Role：
- Relation：
- Rule：核心流程与失败路径
```

### 阶段 2：系统地图与所有权

建立最小系统地图：

- 用户入口、路由、应用/包/模块；
- 数据源、状态所有者、缓存与持久化；
- 公共服务：认证、配置、监控、埋点、国际化；
- 构建产物、部署单元、运行环境；
- 代码所有者、发布所有者和跨团队接口。

重点寻找：隐式共享状态、循环依赖、无所有者公共包、仓库边界与部署边界错位、同一业务规则多处实现。

### 阶段 3：核心业务闭环

选择 1–3 个高价值流程，逐步追踪：

1. 用户或外部事件如何进入；
2. 权限与输入在哪里校验；
3. 数据从哪里读取、由谁拥有、如何缓存；
4. 状态在哪里变化，竞态和取消如何处理；
5. 成功、失败、超时、离线和重试如何反馈；
6. 如何被测试、观测、灰度和回滚。

用时序图或状态图表达 Rule。仅凭目录结构不能证明业务闭环正确。

### 阶段 4：边界与依赖

检查：

- 模块职责是否围绕稳定业务能力或明确变化轴；
- 依赖方向是否能用 lint、构建图或 code owner 约束；
- 公共层是否变成无边界的“垃圾场”；
- UI、业务规则、数据访问和基础设施是否互相渗透；
- 跨应用通信是否有版本、错误和兼容契约；
- Monorepo/微前端是否确实匹配团队与发布边界。

边界问题要说明实际变化半径，例如“一处协议调整需要同时修改 4 个无所有权模块”，不要只写“耦合高”。

### 阶段 5：运行时质量属性

按主要复杂度选择性检查：

| 领域 | 证据 | 常见问题 |
|---|---|---|
| 性能 | RUM、实验室测量、Profiler、Bundle 报告 | 网络/主线程/渲染/水合/缓存瓶颈 |
| 可用性 | 错误率、白屏、事故、回滚记录 | 故障未隔离、无降级、不可恢复状态 |
| 安全 | 信任边界、CSP、认证、依赖扫描 | 客户端秘密、XSS、越权、第三方脚本风险 |
| 状态 | 状态图、缓存策略、并发请求 | 所有权不清、竞态、失效与回滚缺失 |
| 跨端 | 兼容矩阵、真实设备数据 | 能力差异被隐藏、适配层泄漏 |

性能结论必须包含场景、设备/网络、样本、基线与测量方法。实验室成绩不能自动代表真实用户。

### 阶段 6：交付与治理

检查从提交到生产的反馈链：

- 类型、lint、单元/组件/集成/E2E 测试分别保护什么；
- 构建是否可复现，缓存是否正确失效；
- 变更影响范围能否被依赖图或受影响测试识别；
- 配置、环境变量、feature flag 和制品是否可追溯；
- 发布、灰度、监控和回滚是否形成闭环；
- 架构规则是文档约定，还是有自动门禁。

测试覆盖率只能提示范围，不能替代关键业务场景、契约和失败路径的验证。

### 阶段 7：风险排序与行动计划

每条发现包含：

```markdown
### [优先级] 标题
- 状态：事实 / 推断 / 未知
- 位置或范围：
- 触发条件：
- 用户/业务/团队影响：
- 证据：
- 根因假设：
- 建议：
- 验证与退出条件：
- 剩余风险：
```

行动计划按依赖关系排序，而不是把所有“高严重度”同时开工：

1. **止血**：安全、数据损坏、生产故障和不可回滚风险；
2. **建立安全网**：观测、特征测试、契约和发布保护；
3. **局部优化**：消除阻碍目标架构的高收益问题；
4. **架构迁移**：按业务切片迁移边界、状态或部署单元；
5. **治理固化**：依赖规则、owner、模板、门禁与演进触发点。

## 风险分级

综合以下维度，不使用伪精确公式：

- 影响：用户、数据、安全、收入、合规、交付范围；
- 可能性：触发频率和前置条件；
- 可恢复性：自动恢复、人工回滚、不可逆；
- 暴露面：单模块、单产品、全平台；
- 证据置信度：事实强弱与未知项。

建议分级：

- **P0**：正在发生或高度可能造成重大安全、数据或核心业务损害，需要立即止血；
- **P1**：高影响且有可信触发路径，近期安排并明确 owner；
- **P2**：中等影响或需要更多证据，进入计划并设置验证点；
- **P3**：机会型改进或偏好，不阻塞当前目标。
