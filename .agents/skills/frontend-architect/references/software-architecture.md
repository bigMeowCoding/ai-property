## 4R：统一描述语言

架构是在某一抽象层级上看到的系统顶层结构。4R 用四个问题固定讨论边界：

| 维度 | 问题 | 前端示例 |
|---|---|---|
| Rank | 当前讨论哪一层？ | 产品、前端系统、应用、业务模块、组件/基础设施 |
| Role | 这一层由哪些职责单元组成？ | App Shell、业务域、设计系统、状态服务、API Client |
| Relation | 角色如何连接？ | 导入依赖、props/events、HTTP、共享包、运行时协议 |
| Rule | 角色怎样协作完成场景？ | 路由 → 鉴权 → 取数 → 渲染 → 交互 → 错误恢复 |

Rank 不是通用固定编号。先用业务语义命名当前层级，再说明相邻层。不同项目可以有不同层数，不把 L0–L4 当成标准答案。

### Role 的两个视角

- **业务模块视角**：按领域能力拆分，例如商品、订单、支付；
- **物理组件视角**：按构建/部署单元拆分，例如 Web 应用、Remote、BFF、CDN。

同一名称可能在两个视角含义不同。架构图必须说明视角，不能把业务模块、源码目录和部署容器混在一层。

### Relation 要落到契约

关系至少说明：方向、协议/接口、数据所有权、版本与兼容、失败语义、所有者。真正的架构边界需要落实到包 exports、lint 规则、类型/Schema、运行时隔离、CI 门禁或 code owners。

### Rule 要覆盖失败路径

对核心流程同时描述成功、超时、取消、重试、重复提交、离线、权限失败和回滚。静态图表达 Role/Relation；时序图、状态图或决策表表达 Rule。

## 架构设计三原则

### 合适：匹配真实约束

匹配业务阶段、团队技能、时间、兼容性、合规、运维和已有资产。“大厂同款”“最新版本”不是证据。

### 简单：控制总体复杂度

简单不是文件少，而是角色更少、关系更清晰、故障模式可理解、迁移和回滚成本可控。引入工具消除一类复杂度时，必须计算它新增的治理复杂度。

### 演化：为下一步保留触发点

不预测所有未来需求。定义当前方案、容量/协作边界和触发下一演进的可观察信号，例如发布等待、变化半径、构建瓶颈、真实用户性能或团队所有权变化。

## 识别主要复杂度

通用复杂度包括性能、可用性、可扩展性、成本、安全和规模；前端常表现为：

| 复杂度 | 可观察问题 | 可能机制 |
|---|---|---|
| 状态与数据 | 竞态、缓存陈旧、跨页面不同步 | 所有权、失效、并发与回滚不清 |
| 渲染与体验 | 加载慢、交互卡、布局抖动 | 网络、主线程、渲染、水合、媒体资源 |
| 变化与协作 | 改一处牵连多处、发布互相等待 | 边界、依赖方向、团队/部署边界错位 |
| 跨端与兼容 | 行为不一致、适配逻辑散落 | 能力模型、适配层和测试矩阵缺失 |
| 可用与恢复 | 白屏、输入丢失、回滚慢 | 故障隔离、降级、持久化和发布保护不足 |
| 安全与合规 | XSS、越权、秘密泄露 | 信任边界、认证、第三方脚本和数据处理 |

识别步骤：

1. 从用户、业务和团队症状出发；
2. 收集能复现或量化症状的证据；
3. 建立“约束 → 架构机制 → 影响”的因果链；
4. 选出当前最重要的 1–2 个复杂度；
5. 写出反证和仍未知的部分。

技术栈旧、目录不漂亮、文件很长可能是风险信号，但不是架构问题的充分证据。

## 架构决策流程

### 1. 识别复杂度

输出业务目标、约束、现状 4R、主要复杂度和证据。

### 2. 形成备选方案

只有存在真实取舍时才比较 2–3 个方案。把维持现状或局部改进作为基线，避免所有方案都隐含“大改造”。方案差异应体现在角色、关系、规则或迁移路径，而不仅是换工具名。

### 3. 评估并选择

按当前业务优先级讨论：用户体验、可靠性、安全、交付速度、认知负担、迁移风险、运维成本、可逆性和未来触发点。可以用决策矩阵展示事实，但不要把任意权重的总分当成答案。

### 4. 详细设计

至少落实：

- 目标 4R 与核心流程；
- 模块、包、应用、部署和团队边界；
- 状态/数据所有权，接口与事件契约；
- 渲染、缓存、错误、降级和恢复策略；
- 质量门禁、观测、灰度、回滚；
- 分阶段迁移、验收指标和 ADR。

## 业务阶段与演进

业务阶段是输入，不是自动选型表：

| 阶段信号 | 主要目标 | 常见动作 |
|---|---|---|
| 验证期 | 快速验证价值、控制成本 | 熟悉的单体方案、少量约束、可观测核心流程 |
| 快速增长 | 控制变化半径和体验退化 | 业务模块化、状态归属、性能预算、基础测试 |
| 多团队并行 | 明确所有权和独立交付 | 包边界、Monorepo 治理；必要时运行时拆分 |
| 多产品/平台 | 复用稳定能力、保留差异 | 设计系统、共享领域模型、适配层、平台化服务 |
| 稳定优化 | 可靠性、成本与精细体验 | RUM、故障演练、增量构建、专项优化 |

引入微前端、Monorepo、SSR 或跨端框架必须由实际信号触发，不能只由阶段名称触发。

## 架构模式的前端使用

### 分层

用于隔离变化和控制依赖方向。分层名称服从项目，可按 View/Feature/Domain/Data/Infra，也可采用垂直业务切片。核心是规则能被执行，而不是目录长得像模板。

### 服务/应用拆分

适合明确团队所有权和独立发布需求。微前端不是“前端版微服务”的直接等价物；浏览器运行时、单一用户体验、共享依赖、路由和样式使它有独特成本。

### 微内核/插件

适合核心稳定、扩展点明确且第三方或多团队需要扩展的系统。关键是插件生命周期、能力权限、版本兼容、隔离和故障传播。

### 性能模式

CDN、缓存、代码分割、预取、Worker、虚拟化和渲染策略应从瓶颈证据出发。后端的负载均衡、分片或事件循环只能提供思考视角，不能直接等同于浏览器方案。

### 高可用模式

前端重点是故障隔离、可恢复状态、清晰反馈、降级、离线/弱网和安全发布。CAP 适用于共享数据的分布式系统；不要把所有客户端状态问题简化为“前端 AP 优先”，应按业务数据语义选择一致性与可用性策略。

### 可扩展模式

“拆”的目标是控制变化半径。按流程分层、按业务域拆模块、按部署/团队拆应用、按功能建插件可以组合使用。每次拆分都要说明新增通信、治理和认知成本。
