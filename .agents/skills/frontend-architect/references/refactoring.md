# 前端架构重构策略

## 先判断是否需要架构重构

架构重构通常改变 Role、Relation、Rule 或部署/团队边界；代码重构通常在保持可观察行为的前提下改善内部设计。

| 信号 | 更可能是局部代码问题 | 更可能是架构问题 |
|---|---|---|
| 影响范围 | 单函数、组件或模块内部 | 多模块、应用、团队或部署单元 |
| 变化内容 | 命名、重复、复杂条件、局部性能 | 数据所有权、依赖方向、接口、发布边界 |
| 解决方式 | 小步重构和测试 | 目标架构、迁移期共存、灰度回滚 |
| 验收 | 行为不变、测试通过 | 业务/协作指标改善且系统持续可用 |

判断问题：如果从零设计当前系统，顶层结构与现状是否显著不同？如果差异只在局部实现，优先局部优化；如果差异涉及系统角色和协作规则，才进入架构重构。

## 架构重构三式

### 有的放矢：只解决核心复杂度

- 从事故、交付周期、性能数据、变化半径和协作阻塞中找证据；
- 聚焦 1–2 个主要问题，不把升级依赖、整理目录和修所有债务捆成一次“大重构”；
- 写清“不做什么”，避免重构范围随实施膨胀；
- 先确定目标指标与退出条件，再选技术。

### 合纵连横：把技术收益翻译成业务结果

利益相关方通常关心：上线周期、故障范围、回滚速度、回归成本、用户体验、合规和预算。用已有数据或待验证假设说明收益，不用“架构先进”“技术统一”代替价值。

建立责任表：决策者、业务 owner、迁移模块 owner、测试、运维/平台、受影响系统与沟通节奏。若缺少必要合作，不伪装成纯技术问题。

### 运筹帷幄：先救火、后安全网、再迁移

1. **止血**：隔离故障、限制影响、补回滚能力；
2. **安全网**：监控、特征测试、契约测试、兼容层；
3. **预备性重构**：在不改变边界时清理迁移入口；
4. **按业务切片迁移**：每个切片可独立验证和回滚；
5. **收口**：迁移消费者、停止双写、删除旧路径、固化门禁。

阶段长度由业务和风险决定，不预设固定周数或月份。

## 迁移设计

### 写清不变量和允许改变项

```markdown
## 迁移契约
- 目标：
- 范围：
- 必须保持：用户行为、公共接口、数据语义、兼容范围……
- 允许改变：内部模块、部署方式、缓存、构建链……
- 暂不处理：
- 目标指标与基线：
```

### 选择迁移接缝

优先选择有明确输入输出、可观测、可回退的边界：路由、API 适配层、事件契约、包导出、feature flag、代理/网关、组件外壳。若系统没有接缝，先用代码级重构建立接缝。

### 设计共存期

常用策略：

- **绞杀者模式**：新路径逐步接管业务切片；
- **适配层**：隔离旧协议与新模型；
- **影子流量/双读**：比较结果但不影响用户；
- **双写**：仅在能处理幂等、顺序、冲突、补偿和停写时使用；
- **feature flag**：按用户、租户或流量切换，并保证 flag 本身可观测和可清理。

共存会引入额外复杂度。必须定义开始条件、观测指标、最长容忍期和退出动作。

### 每个切片的闭环

```markdown
### 切片 N
- 用户/业务范围：
- 旧路径 → 新路径：
- 依赖与数据迁移：
- 代码实施任务：
- 上线和灰度：
- 验收：
- 回滚触发与步骤：
- 收口动作：
```

具体代码任务交给 `code-craft-and-refactoring`，保持小 diff、先测试后重构、功能变更与重构分帽子。

## 常见迁移类型

### 分层与模块边界

- 先建立依赖图和目标方向；
- 以业务切片迁移，不按文件类型一次性搬目录；
- 用 lint、包 exports、构建边界或 code owners 固化规则；
- 公共层只承载稳定、跨域且有 owner 的能力。

### 状态与数据所有权

- 先分类 URL、局部 UI、跨组件客户端状态、服务端状态和持久化状态；
- 为每类状态定义唯一 owner、更新入口、缓存失效和错误/回滚语义；
- 新旧 store 可短期并存，但避免无期限双向同步；
- 迁移工具不应改变业务数据语义。

### 构建工具或框架升级

- 先核对官方迁移文档、兼容矩阵和生态阻塞项；
- 建立等价构建、测试和运行基线；
- 把语法迁移、行为变化、依赖替换和架构调整分开；
- 不默认“新工具一定更快”；在真实项目上测量冷启动、增量构建、CI 和产物。

### Monorepo 或微前端

- 目标应是解决所有权、共享代码、独立发布或构建规模问题，而不是追求形式；
- 仓库边界、包边界、运行时边界、部署边界和团队边界分别设计；
- 先具备自动化测试、发布、版本与观测能力，再增加运行时拆分；
- 明确共享依赖、路由、认证、样式、错误隔离和跨应用通信契约。

### 渲染策略迁移

CSR、SSR、SSG、流式渲染或边缘渲染的选择应按路由/页面评估 SEO、个性化、数据新鲜度、运行成本、水合和缓存。不要为了采用框架能力而全站迁移。

## 验收与交接

架构验收至少包括：

- 目标业务指标相对基线的变化；
- 核心流程、失败路径和兼容性验证；
- 新边界、依赖方向和契约被门禁保护；
- 灰度、监控和回滚演练；
- 旧路径、临时适配、feature flag 和双写的清理状态；
- 剩余风险、未知项和下一阶段触发条件。

交付时区分：已完成且有证据、已完成但待线上验证、未完成、明确不做。不要把计划写成结果。
