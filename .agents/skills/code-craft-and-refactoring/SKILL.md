# 代码精进与重构

把代码质量视为一个完整工程闭环：先理解真实问题与现有行为，再选择最小而有价值的改变，最后用测试、编译器、静态分析和差异审查提供证据。

## 不可妥协的原则

1. **先解决真实问题**：不要为了“更漂亮”而改动稳定且无需触碰的代码。
2. **保持行为**：重构不改变可观察行为；功能变更与重构要分开戴“两顶帽子”。
3. **小步反馈**：一次只做一个可解释、可撤销的改变，并尽快运行最相关的验证。
4. **证据优先**：评审结论要能指向代码路径和触发条件；性能优化要有基准；安全判断要有信任边界与数据流。
5. **质量因地制宜**：优秀代码追求经济、规范、安全，但具体做法服从用户要求、仓库规则、团队约定和语言生态。
6. **不要伪造确定性**：未运行的测试、未复现的缺陷、未测量的性能不得写成已验证事实。

## 与前端架构技能协作

当任务同时涉及前端系统边界和代码落地时，联合使用 `frontend-architect`：

- `frontend-architect` 负责 Rank/Role/Relation/Rule、目标架构、契约、不变量、迁移切片、灰度回滚与架构验收。
- 本技能负责理解现有行为、预备性重构、最小安全实现、测试、静态检查、性能/安全证据与最终 diff。
- 架构交接必须写清目标、范围、不可改变行为、允许改变项、每阶段验收和回滚条件；信息不足时先标记未知，不自行补造架构前提。
- 单个函数、组件或局部坏味道默认只用本技能；只有改变跨模块依赖、数据所有权、团队/部署边界或核心协作规则时才升级为架构任务。

## 工作流

### 1. 对齐任务与约束

- 判断用户要的是解释、诊断、评审，还是实际修改。
- 读取仓库说明、相关文档、测试和已有实现；仓库规则优先于本技能的风格建议。
- 明确成功条件、不可改变的行为、兼容性边界和允许的变更范围。
- 区分事实、推断和偏好。风格偏好不能伪装成正确性缺陷。

### 2. 建立行为与风险模型

- 从一个用户入口、调用方、示例或测试开始，沿接口进入实现，再追踪关键依赖与状态变化。
- 同时回答：输入来自哪里、输出给谁、状态在哪里变化、错误如何传播、哪些资源或权限被触碰。
- 对旧代码先建立基线：运行最小相关测试；若无测试，优先补特征测试或把改动缩到可人工证明的局部。
- 按用户影响评估风险：严重性 × 发生可能性；安全、数据损坏、权限绕过和广泛兼容性问题默认提高优先级。

### 3. 选择最小有效行动

**写新代码**：先从调用者角度确定接口与失败行为；优先复用现有抽象；实现当前必须做的最小方案；用测试定义关键行为。

**修改旧代码**：先定位真正的变化点；需要时做预备性重构；每步保持可运行，并控制 diff 只包含相关改动。

**重构**：先确认测试绿灯；选择一个坏味道和一个对应手法；执行一个微小步骤；复跑测试；再决定是否继续。

**代码评审/诊断**：保持只读，除非用户明确要求修复。优先寻找会改变用户行为、数据、权限、并发时序或兼容性的具体问题。

**性能优化**：先定义用户可感知指标和资源指标，建立可复现基准，定位热点后再优化；优化后对比结果并检查行为回归。

**安全分析**：从每个信任边界追踪未可信数据，检查校验、授权、敏感信息、整数边界、可变共享状态和序列化；不要只搜索危险 API 名称。

### 4. 运行质量流水线

按成本从低到高获取反馈：

1. 格式化、类型检查或编译器警告。
2. 最小相关单元/特征测试。
3. 模块级或集成测试。
4. 静态分析、安全扫描或性能基准（适用时）。
5. 检查最终 diff：确认无无关改动、调试残留、接口漂移和测试空洞。

若某项无法运行，说明原因、已完成的替代验证和剩余风险。

### 5. 交付结果

- **实现任务**：先说明完成了什么，再说明关键设计、验证结果和仍存在的风险。
- **评审任务**：先列发现，按优先级排序；每条包含位置、触发条件、用户影响、证据和最小修复方向。没有发现就明确说没有发现，并列出验证边界。
- **建议任务**：把“必须修复”“值得改进”“风格偏好”分开，避免把清单当成机械打分表。

## 决策优先级

当建议冲突时，按以下顺序取舍：

1. 用户目标与可观察行为正确。
2. 数据、安全、权限与兼容性不受破坏。
3. 仓库规则、公共接口合约和团队约定。
4. 可验证性、可理解性与最小变更范围。
5. 性能、扩展性和复用的实测收益。
6. 个人审美与通用风格偏好。
