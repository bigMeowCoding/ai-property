# 代码任务闭环

本文件把代码阅读、变更和质量流水线连接成一个可重复工作流。

## 1. 从外到内阅读

按以下顺序建立上下文，避免一开始扎进实现细节：

1. 读取 README、设计说明、仓库规则和用户文档。
2. 找到一个用户入口、公开接口、示例或测试用例。
3. 沿调用链进入实现，记录关键模块、状态和外部依赖。
4. 查找对称实现、同类模块和所有调用方，辨别局部约定与系统不变量。
5. 回到测试，确认正常、边界和失败路径实际覆盖了什么。

阅读时持续回答：谁调用它、输入来自哪里、输出给谁、状态在哪里改变、错误如何传播、资源何时释放。

## 2. 建立变更基线

修改前收集最小充分证据：

- 当前测试、类型检查、编译或 lint 是否通过。
- 用户描述的问题能否通过测试、日志、调用路径或最小示例复现。
- 当前 diff 中哪些改动属于用户，哪些属于本任务；不要覆盖无关工作。
- 公共 API、数据格式、数据库、并发时序、权限和外部副作用是否在变更边界内。

没有测试时按风险选择：

- 可观察既有行为：补特征测试，再重构。
- 极小、机械、可静态证明的改动：缩小范围并检查 diff。
- 高风险且无法建立安全网：停止扩张，报告缺口与剩余风险。

## 3. 设计最小变更

用一句话描述改变：`在 <触发条件> 下，把 <旧行为> 改为/保持为 <目标行为>`。

然后确认：

- 是否能复用现有接口或惯用模式。
- 是否需要预备性重构让新功能容易加入。
- 是否把功能修改、重构、格式化和依赖升级混在同一个 diff。
- 是否引入了只为假想未来服务的抽象。
- 是否存在更小、更容易回滚和验证的路径。

## 4. 小步实施

每个步骤只做一类改变：

1. 先写或调整能表达目标行为的测试。
2. 做最小实现或一个重构手法。
3. 运行最相关的快速验证。
4. 检查失败是否由本步引起；绿灯后再继续。
5. 在清晰节点检查 diff，必要时提交或保留可回滚边界。

重构期间测试变红时，先回到最近的绿灯状态；不要在红灯上叠加更多结构修改。

## 5. 分层验证

按风险和反馈速度逐层扩大：

| 层级 | 目的 | 常见手段 |
|---|---|---|
| 静态反馈 | 捕获语法、类型、格式和显性规则问题 | formatter、compiler、typecheck、lint |
| 局部行为 | 验证本次改变的直接契约 | 单元测试、特征测试、最小复现 |
| 模块交互 | 验证依赖、状态和错误传播 | 集成测试、组件测试 |
| 用户闭环 | 验证入口到结果的真实路径 | 端到端测试、UI/CLI/API 走查 |
| 专项风险 | 验证特定非功能目标 | 基准、profiler、并发测试、安全扫描 |

测试数量服从风险，不服从仪式。优先覆盖失败后代价最高的路径。

## 6. 最终差异审查

交付前检查：

- diff 是否只包含任务相关变化。
- 测试是否真正断言目标行为，而不是只执行代码。
- 错误和资源清理路径是否完整。
- 公共接口、数据结构和文档是否同步。
- 是否留下调试输出、临时开关、死代码或压制警告。
- 性能/安全结论是否附带测量方法或数据流证据。

## 7. 结果表达

把结果分为三类：

- **已验证**：写明运行了什么以及结果。
- **静态推断**：写明依据和尚未执行的验证。
- **剩余风险**：写明为什么未覆盖、影响范围和建议下一步。

评审发现使用：`优先级 + 位置 + 触发条件 + 用户影响 + 证据 + 最小修复方向`。优先级来自影响严重性与发生可能性，不来自个人偏好。
