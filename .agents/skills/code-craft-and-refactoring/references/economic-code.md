# 经济代码与性能参考

经济代码追求全生命周期投入产出，而不只是运行速度。先减少不必要的需求和复杂度，再优化真正的资源热点。

## 三层指标

1. **用户感受**：延迟、吞吐、成功率、卡顿、成本或电量等真实体验。
2. **资源效率**：CPU、内存、磁盘、网络、连接、线程和外部服务配额。
3. **算法性质**：时间/空间复杂度及其在真实数据规模下的表现。

优化前定义基线、数据集、环境和目标；优化后用同一方法对比。微基准只证明局部，不自动证明系统或用户体验改善。

## 需求评审

- 需求是真实且普遍的，还是臆测出来的？
- 什么必须做？什么现在必须做？能否分解、简化或推迟？
- 失败代价与优化收益是否值得新增代码和长期维护成本？
- 是否已有接口、库、平台能力或配置可以复用？

## 设计评审

- 接口是否简单直观、只承担一个逻辑层次的完整职责？
- 状态、依赖和资源生命周期是否明确？能否优先采用不可变或无共享状态？
- 是否为真实变化设计，还是为假想未来建立复杂抽象？
- 并发是否必要？能否通过单线程、分区、消息传递或不可变数据避免同步？
- 水平扩展是否被会话、缓存或本地状态阻碍？有状态与无状态数据是否可以分离？
- 是否需要同步执行；异步化是否真的改善瓶颈，还是转移复杂度？

## 代码评审

- 是否重复实现已有能力，或为了“复用”制造了不自然的抽象？
- 是否有无界集合、缓存、队列、重试或并发任务？
- 大对象、频繁分配、拷贝和序列化是否处于热路径？
- I/O、连接、文件、锁和线程是否在所有路径可靠释放？
- 锁范围能否缩小；锁顺序是否可能死锁；共享状态能否消除？
- 哈希键的相等性和哈希实现是否正确，是否存在极端冲突？
- 延迟初始化是否值得新增线程安全、错误缓存和生命周期复杂度？
- 清理、重排或缓存是否改变了调用顺序、可见副作用或一致性？

## 常见陷阱

| 信号 | 先调查 | 常见方向 |
|---|---|---|
| 循环字符串拼接 | 语言/编译器是否已优化、输入规模 | builder、join、流式写入 |
| 长生命周期集合 | 增长是否有界、淘汰是否执行 | 上限、TTL、主动清理、可观测性 |
| 资源未关闭 | 异常与提前返回路径 | 确定性清理机制 |
| 共享可变状态 | 是否真的需要共享 | 不可变、分区、复制、消息传递 |
| 过早分配 | 实际使用率和初始化成本 | 延迟分配，但衡量额外复杂度 |
| N+1 或重复 I/O | 调用次数、批量能力、缓存一致性 | 批处理、合并请求、合适缓存 |

`WeakReference`、对象池、单例和缓存都不是默认答案：它们可能增加 GC、并发、泄漏或一致性风险，必须结合运行时特性和基准选择。

## 优化闭环

1. 选择用户指标与资源指标。
2. 构造可复现负载并记录基线。
3. 用 profiler、trace 或统计定位热点。
4. 一次改变一个主要因素。
5. 对比性能结果，并运行行为回归测试。
6. 记录环境、方法、收益和权衡；收益不足就回退复杂化方案。
